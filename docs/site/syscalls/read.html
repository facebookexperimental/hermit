read (0)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-20 at 403e350e9e82

In short

Natively, read copies up to the requested count from a descriptor's current position and returns how many bytes it copied, so a short copy, end of file, a wait for a writer, and the host file's own contents all show in the answer. Outside a DBT copied child, which runs it natively, Hermit forwards ordinary descriptors to the host kernel on the ptrace family and to the backend's own Linux provider on KVM, runs the call inside its serialized schedule, answers the random devices and the files it renders itself from its own model, and retries a regular file's short copies until the request is full or the file ends whenever deterministic I/O is on, which is the default in a plain run. The sibling calls readv and pread64 share parts of this handler family and keep their own pages; they are cross-linked here and are not checked on this page. Known gaps: 14.

Determinism strategy

What is nondeterministic natively. read takes the descriptor's file, checks it can be read, checks the destination, and copies from the current position, advancing that position by what it copied.[linux] How much it copies on one call is the host's answer: a pipe or socket may give less than asked because only that much had arrived, a regular file usually gives less only at end of file though the kernel caps one call and some special files return short copies sooner, and a blocking descriptor waits until data or end of file arrives, so arrival timing decides both the count and when the call returns.[linux]

What Hermit does. Outside a DBT copied child, Detcore determinizes read by handling it with the shared typed handler for the read family: classification places the entry with the determinized calls, and typed dispatch reaches the handler — a diagnostic-socket descriptor takes its own arm first, whose reply identities are canonicalized and whose counters are zeroed where metadata is virtualized — and notes the receive for any descriptor passing afterwards.[c1][c2][c27] Two takes run before that dispatch and own the call where they apply: on LiteInst in-guest alone, in a process that handles the virtual alarm signal, a phase gate admits only a memory descriptor, a rendered snapshot whose capture cannot wait, and a narrowly gated guest-held polled pipe, and refuses every other read before the handler runs (see the refusal order below); and in the networking trace modes a read of a recorded channel socket is answered from the trace path before dispatch, with a zero-count call returning zero without a kernel call and a replay serving the traced bytes (detcore/src/syscalls/network_trace.rs).[c36][c21] The ptrace family is every backend except KVM (ptrace including e9patch preprocessing, DBT, SaBRe and LiteInst). Inside the handler, the unknown-sequence refusal comes first among handler refusals, then a shared sequence where a fork shares one, then a timer-slack binding and a rendered command-line file from memory, each in the order stated below.[c3][c13][c12] A zero-count call is special: on a random device it still checks the descriptor can be read and that the destination is valid and returns zero; on any other descriptor except an inotify instance its answer goes through record/replay, because a replayed placeholder can fail differently; a zero-count read on a socket consumes nothing, exactly as the kernel leaves a pending message in place for this call; an inotify zero-count call waits like its other calls.[c4][linux] A rendered file that serves a snapshot checks the descriptor can be read before it looks at the destination — EBADF first, as the kernel does — then validates the destination range, adopts the record position, drops a stale snapshot where the read does not continue the sequence, and copies from its preview, advancing the shared cursor only by what copied.[c5][c22] Most descriptors take no per-description grant at all: only container standard input, output and error and inherited terminals carry an open-file resource, and ordering otherwise comes from sequentialized threads running one guest turn at a time, with no ordering promised where threads are not sequentialized (the resource defaults to none in the descriptor model, detcore/src/fd.rs).[c28] What happens next is chosen by the descriptor's kind among regular, memory, process, userfault, event-poll, pipe, socket, event, timer, signal, inotify and diagnostic-socket descriptors.[c23] A random device never reaches the kernel: Detcore fills the destination from its seeded canonical stream at the descriptor's own offset, after checking the descriptor can be read.[c7][c8] A regular file with deterministic I/O enabled goes through the retry loop below; without it, and for memory, process, userfault and event-poll descriptors, the single forwarded answer goes through record/replay, on the host kernel for the ptrace family and on the backend's Linux provider for KVM (reverie-linuxemu/src/executor/read_write.rs, reverie-linuxemu/src/executor/dispatch.rs, reverie-kvm/src/runtime.rs).[c23][c6][c9] A pipe or socket, and an event or timer descriptor, goes through the nonblockable path: the descriptor is made physically nonblocking where the peer is inside the run and the call retries in guest turns, while a descriptor whose peer is outside, or any such call while threads are not sequentialized or under record/replay for an outside peer, runs as one blocking forwarded call through record/replay.[c10][c23] A signal descriptor reads its records through that same path, dropping stale entries and reading again where every record was dropped, and a timer descriptor whose virtualized count is modeled returns the model's expiration count where virtual time, sequentialized threads and a plain run all hold.[c23][c24][c25] An inotify read has each nonzero rename cookie replaced by a virtual cookie before the guest sees the events.[c26]

Interface fidelity. The count, the bytes, the position advance and end of file are the executor's for every descriptor Detcore forwards — the host kernel on the ptrace family and the backend's Linux provider on KVM (reverie-linuxemu/src/executor/read_write.rs, reverie-linuxemu/src/executor/dispatch.rs, reverie-kvm/src/runtime.rs) — because it copies with the guest's own call and returns its count unchanged outside the modeled and rewritten answers above and the deterministic-I/O retry.[c9][linux] The modeled and rewritten answers are these: the seeded random-device stream, the rendered-file preview copy, the modeled timer expiration count, the virtual inotify rename cookies, the canonicalized diagnostic-socket reply, and the signal-descriptor drop and re-read, each as stated above.[c7][c22][c24][c26][c27] The deterministic-I/O retry is one place the returned count can differ from any single forwarded call: with deterministic I/O enabled, a regular file is read again at the advanced destination until the request fills or a call returns zero, and an error after some bytes copied returns those bytes instead of the error — exactly the call sequence a guest that loops on short reads would make, folded into one call.[c9] It does not run for any other kind: an inherited external regular file or pipe is one blocking record/replay call and is never filled, and a pipe or socket fills only by arriving data through the retry-in-turns path, never by this loop.[c23][c6][c10] A short copy that faults part-way keeps the executor's rule that bytes already copied count for forwarded kinds: a faulting rendered copy of a random UUID, a pty count or a fixed file that is not a seq_file instead returns EFAULT and commits nothing, while seq_file-backed rendered files commit what was copied, and a fault before any copy on forwarded kinds leaves the position where it was.[c30][linux] There are no flags or options on this call to honor or coalesce; its only arguments are the descriptor, the destination and the count, and a missing destination on a modeled answer is EFAULT where the forwarded call's own copy gives the same answer for a forwarded one.[c7][linux]

Every refusal, in the order it is decided. First, on LiteInst in-guest alone, in a process that handles the virtual alarm signal, the phase gate refuses every read it does not admit — a regular file, a socket, a named FIFO, container standard input, an event descriptor and an unmodelled descriptor among them, and an unknown descriptor where the kernel would give EBADF — with EOPNOTSUPP before any dispatch; only a memory descriptor, a rendered snapshot whose capture cannot wait, and a narrowly gated guest-held polled pipe reach the handler in that process (the gate is armed only where the backend virtualizes the guest alarm signal, reverie/src/capabilities.rs).[c20][c21] Second, a placeholder directory answer comes before dispatch: a served directory descriptor that cannot be read gives EBADF, then a bad destination gives EFAULT, then a directory gives EISDIR, each as Linux answers them for procfs's root and for a descriptor directory, in Linux's order of checks; a placeholder received without sequentialized threads is refused by name, and a failed adoption of a received rendered descriptor is answered before either, and only those two diverge.[c29] Third, in the networking trace modes, a read of a recorded channel socket is taken by the trace path before dispatch and ends as that path decides (detcore/src/syscalls/network_trace.rs).[c36] Fourth, a descriptor whose rendered record sequence Detcore cannot know here, through a descriptor that can read, is refused: under --allow-unsupported-syscalls the call gets EOPNOTSUPP on every backend; otherwise a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit, ends on DBT through its runtime exit path, and on SaBRe alone gives EOPNOTSUPP with no process ending and the reason on the guest's standard error where stopping would strand the run. A descriptor that cannot read never reaches this refusal and keeps EBADF below.[c11] Fifth, a descriptor Detcore lists without modelling — a received anonymous inode, a receipt whose facts could not be taken, or an unaccounted receipt — fails from the model lookup with EBADF for any count before the zero-count path, on the ptrace backend, KVM and LiteInst, where the kernel would read the descriptor; the other backends discover such a descriptor instead, as the same unmodelled-descriptor divergence the ioctl page carries.[c3] Sixth, a rendered file whose sanitize step fails, a first-read render failure, a signal descriptor whose records cannot be served, a received inotify instance that blocks on the host, and one whose blocking mode is unknown with nothing queued are each refused: a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit, ends on DBT through its runtime exit path (the sanitize gate calls the shutdown directly, bypassing that path's report, so it likewise ends only the refusing process), and on SaBRe ends only the refusing process so the run can wait on stranded; otherwise the read gives EIO for the render cases, ENOSYS for the signal case, and for inotify the blocking-host refusal exists only in a fail-closed run while under the opt-in the read waits in the host and the unknown-mode case gets EAGAIN. A blocking inotify read that the backend answers with EAGAIN is refused by name under fail-closed, and a virtual timerfd whose expiration cannot be published refuses the run.[c31][c32][c33][c34][c24] Seventh, a timer-slack binding answers EBADF for a descriptor that cannot read and then checks its target before the destination fault the kernel checks first.[c35] Eighth, on a rendered command-line file, and on a snapshot file that follows a record sequence, a descriptor that cannot read is EBADF before the destination is looked at; then a destination outside the user address limit, or a count no limit admits, is EFAULT; then a position whose end overflows is EINVAL.[c12][c5][c14] Ninth, on a random device, a descriptor that cannot read is EBADF, then a missing destination is EFAULT.[c7][c8] Last, every forwarded call then takes its executor's own order — the kernel's on the ptrace family and the provider's on KVM (reverie-linuxemu/src/executor/read_write.rs): EBADF for a descriptor that cannot be read, EINVAL where the file cannot read at all, EFAULT for a bad destination, then the range check's own errors, then the file's own errors including EAGAIN on a nonblocking descriptor with nothing to read, with the provider additionally ending the run on a zero-count read it does not admit that could block, capping one forwarded call well below the kernel's cap (MAX_HOST_IO in reverie-linuxemu/src/executor/read_write.rs), checking a directory before the destination, and ending the run for a blocking inotify read and a late socket copy-out fault (reverie-linuxemu/src/executor/read_write.rs, reverie-linuxemu/src/executor/dispatch.rs, reverie-kvm/src/runtime.rs).[linux] The precedence differences from the kernel are each refusal above that the kernel has no counterpart for, in the order stated; the unknown-sequence refusal by construction only applies through a readable descriptor, so no call the kernel would answer EBADF is diverted by it alone.[c11][linux]

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c2] In a plain run the forwarded branches inject the forwarded call directly and the modeled branches (random device, rendered files) need no recording because they are re-derived from seeded and rendered state. Under record, the record/replay path records the forwarded answer — bytes and count — and under replay it returns that answer without reading the host file, pipe or socket again (the recorder stores the bytes and the count and the replayer writes them back without reading the host, hermit-record/src/recorder/fs.rs and hermit-replay/src/replayer/fs.rs, with an event-descriptor placeholder's side effect re-injected as the one exception), so replay repeats the recorded short count and end of file even if more data has since arrived.[c23] Deterministic I/O is off under record and replay, so the folded regular-file retry does not run there (the record and replay configuration turns that mode off, hermit-cli/src/bin/hermit/run.rs and hermit-cli/src/metadata.rs).[c9] The internal pipe and socket retry path runs in every mode: a descriptor whose peer is inside the run is made physically nonblocking and its data is captured by that path; under record each attempt is recorded, and under replay each attempt is answered from the recording; an outside peer under record/replay runs as one blocking recorded call.[c10] In the networking trace modes the trace path owns the channel read in both recording and replaying, with replay serving the traced bytes (detcore/src/syscalls/network_trace.rs).[c36]

Known gaps

  • G1 (unimplemented): in a DBT copied child — the window between a vfork and the exec of the child's next program, where no Detcore tool runs — this call runs natively in the kernel, in fail-closed runs and under --allow-unsupported-syscalls alike: it is on the copied child's acknowledged-escape list, is not in the deterministic-refusal set (which by construction excludes ordinary forwarded calls like this one), and the copied-child gate therefore lets it through to the host (inguest-engine/src/native/copied_action.rs).[c18] On the ptrace backend (including e9patch preprocessing, which is not a backend), KVM, SaBRe and LiteInst the same call reaches the handler above except where the phase gate below refuses it first. A guest whose reads in that window must be modeled must avoid the copied-child path; there is no fallback inside the call on DBT.
  • G2 (by design): an ordinary file, pipe or socket is still the host's object outside the modeled answers: its contents, the writer at the other end, and how much had arrived when a forwarded call runs are whatever the host does, so a filesystem or peer that changes under the run, or differs between hosts, changes the bytes and the count, and Hermit makes this call repeatable only so far as that source repeats. On the ptrace backend (including e9patch preprocessing), DBT outside a copied child, SaBRe and LiteInst the executor is the host kernel through the same handler; on KVM the executor is the backend's Linux provider instead, whose own answers are gaps below (reverie-linuxemu/src/executor/read_write.rs, reverie-linuxemu/src/executor/dispatch.rs, reverie-kvm/src/runtime.rs).[c23][c9]
  • G3 (unimplemented): the short-read retry to full length runs only for a regular file and only with deterministic I/O enabled; that mode is on by default in a plain run and always under the strict policy, and off only with the explicit opt-out and under record and replay (the run configuration turns it on unless opted out and the record and replay configuration turns it off, hermit-cli/src/bin/hermit/run.rs and hermit-cli/src/metadata.rs). Without it a regular file's single forwarded answer stands, and for every other kind on every backend (ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst) a short copy is returned as the executor gave it, so a guest that does not loop on short reads sees host arrival timing in its counts.[c9][c23]
  • G4 (unimplemented): a read whose rendered record sequence Detcore cannot know is refused as stated above instead of being answered from a sequence it might have used: a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit and ends on DBT through its runtime exit path for a call Linux would answer, on SaBRe alone the call gets EOPNOTSUPP with no process ending and the reason on the guest's standard error, and under --allow-unsupported-syscalls every backend gives EOPNOTSUPP where Linux would return bytes or end of file. A guest in that case must read through a descriptor whose sequence Detcore knows; there is no fallback for the unknown-sequence descriptor.[c11]
  • G5 (unmeasured): whether a blocking pipe, socket, event or timer read waits in guest turns or as one blocking forwarded call depends on whether the peer is inside the run and on thread sequentialization, and under record/replay an outside peer always takes the blocking form: on the ptrace backend (including e9patch preprocessing), KVM, DBT outside a copied child, SaBRe and LiteInst the returned bytes are the same except where G10 and G11 state otherwise, but no measurement here pins whether an outside writer that never writes leaves the same observable wait, or the same interrupted-read answer, across those configurations.[c10]
  • G7 (by design): the random-device answer is Detcore's seeded stream, not the host device: bytes from a descriptor opened on the character devices numbered 1:8 or 1:9, by whatever name reached them, repeat across runs with the run's seed, where the host device would not repeat. This is the determinism the call is for, stated because a guest measuring entropy quality sees a stream no host device produces, on every backend (ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst); in a DBT copied child the same descriptor reads the host device natively (G1). No fallback to host entropy exists inside the call.[c7][c8]
  • G8 (unmeasured): guest programs file_io_roundtrip and exec_pipe_state under tests/c exercise read-back and pipe reads as text, and no machine-verified coverage at the pin distinguishes the deterministic-I/O retry count or the random-device stream across the ptrace backend (including e9patch preprocessing), KVM, DBT, SaBRe and LiteInst; each is therefore claimed from the handler code above, not from a measured run.[c9][c7]
  • G9 (unimplemented): on KVM alone, a zero-count read the provider does not admit — on an unlisted filesystem, a terminal or other device, or an inotify instance with a valid destination among them (reverie-linuxemu/src/executor/read_write.rs) — ends the run as a terminal provider refusal where Linux returns zero for files and devices (for inotify Linux waits for an event and then returns EINVAL), so a guest in that case has no zero-count probe on KVM; the admitted descriptors return zero without consuming anything.[c4]
  • G10 (unimplemented): on KVM alone, one forwarded read is capped well below the kernel's cap (MAX_HOST_IO in reverie-linuxemu/src/executor/read_write.rs), so a large memfd read and a regular-file read with deterministic I/O off can return short where the kernel would fill more, a directory is checked before the destination in the opposite order to the kernel, and a blocking inotify read and a late socket copy-out fault end the run (reverie-linuxemu/src/executor/read_write.rs); a guest that must move more in one call must loop, and no larger single-call form exists on KVM.[c23][linux]
  • G11 (unimplemented): on LiteInst in-guest alone, in a process that handles the virtual alarm signal, every read the phase gate does not admit — a regular file, a socket, a named FIFO, container standard input, an event descriptor and an unmodelled descriptor among them — gets EOPNOTSUPP before the handler runs, and an unknown descriptor gets EOPNOTSUPP where Linux gives EBADF, so a guest in that process must read only through an admitted descriptor; there is no handler fallback in that process.[c20][c21]
  • G12 (unimplemented): a descriptor Detcore lists without modelling fails with EBADF from the model lookup for any count on the ptrace backend, KVM and LiteInst, where Linux would read the descriptor, so a guest holding such a received descriptor cannot read it there; the remaining backends discover the descriptor instead, as the same divergence the ioctl page carries.[c3]
  • G13 (unimplemented): a rendered file whose sanitize step fails, a first-read render failure, a signal descriptor whose records cannot be served, and a received inotify instance that blocks on the host or whose blocking mode is unknown with nothing queued are each refused as stated above — a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit, ends on DBT through its runtime exit path, and on SaBRe ends only the refusing process so the run can wait on stranded; otherwise the read gives the stated error, with the inotify blocking-host refusal only in a fail-closed run — where Linux would return bytes, so a guest in those cases has no read through that descriptor in that state.[c31][c32][c33][c34]
  • G14 (unimplemented): a placeholder received without sequentialized threads is refused by name, and a failed adoption of a received rendered descriptor is answered before dispatch, each diverging from the kernel; the placeholder directory's EBADF, then EFAULT, then EISDIR answers match Linux for procfs's root and for a descriptor directory, in Linux's order of checks, and are not divergences, so a guest in the two diverging cases meets Detcore's answer and has no forwarded fallback there.[c29]
  • G15 (unimplemented): in the networking trace modes a read of a recorded channel socket never reaches this handler: the trace path answers it, with replay serving the traced bytes (detcore/src/syscalls/network_trace.rs), so a guest in those modes reads the trace and not the host socket; outside those modes this gap does not apply.[c36]
