bind (49)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-20 at 403e350e9e82

In short

Natively, bind gives a socket the local address the guest names — a filesystem or abstract Unix name, a netlink port ID, or an Internet address and port — and where the guest asks for port zero (or no Unix name, or netlink ID zero) the kernel invents the missing piece from host state, so two runs can receive different ports and names. Outside a DBT copied child, which runs it natively, Hermit forwards the named bind to the host kernel on the ptrace family and to the backend's own Linux provider on KVM but takes over the inventions it rewrites: a run-wide deterministic allocator in the global state hands out the ephemeral port, the Unix autobind name and the netlink ID in schedule order, rewriting the address before the executor sees it, and retries a host-busy invented port with the next candidate, while the trace modes and the LiteInst phase gate each own whole classes of bind before this handler as gaps below state. The sibling calls socket, connect, accept and accept4 keep their own pages; they are cross-linked here as the addressing context and are not checked on this page. Known gaps: 20.

Determinism strategy

What is nondeterministic natively. bind looks the descriptor up, copies the address in, and hands it to the protocol's own bind, so a bad descriptor, a non-socket and a bad address pointer fail before any protocol runs.[linux] For Internet sockets the protocol then checks the address and, for port zero, searches the ephemeral range from a random starting offset with an odd-port preference for the first port with no conflicting bind, failing only when that search finds none; an explicit port succeeds or conflicts by the binds the host already holds.[linux] An unnamed Unix socket receives a kernel-chosen abstract name and a netlink socket with ID zero receives a kernel-chosen ID derived from the caller's task, so the invented pieces name host and timing state the guest did not supply.[linux]

What Hermit does. Outside a DBT copied child, Detcore determinizes bind by handling it with the shared typed handler for the socket family: classification places the entry with the determinized calls, and typed dispatch reaches the handler — under the ConnectBind scheduling heuristic the call first files a priority-change request at the lowest priority, so a bind is scheduled after the connects it may serve, to exercise races between them.[c1][c2][c3] Three takes run before that dispatch where they apply: on LiteInst in-guest alone, in a process that handles the virtual alarm signal, the phase gate refuses every bind before the handler; a pathname Unix bind below a served directory and a bind naming a served entry outside the configured level are answered before dispatch; and in the networking trace modes (--record-networking and --replay-networking) every Internet bind, every abstract Unix bind and every bare autobind is owned by the trace path and ends the run before this handler, leaving only a named filesystem Unix bind to reach it, and netlink sockets cannot be created in those modes at all, each as gaps below.[c26][c27][c29] The ptrace family is every backend except KVM (ptrace including e9patch preprocessing, DBT, SaBRe and LiteInst). The handler then reads the address the guest named: a missing address pointer is its own first error (see the refusal order below), any guest-held marking on the descriptor is cleared because a named socket can be reached from outside the run, and the descriptor's open-file identity is taken for the allocator calls that follow.[c3] What happens next is chosen by the address family the first two bytes name. An unnamed Unix bind — family AF_UNIX with an address length that covers only the family, the offset of the path — never reaches the executor as written: the allocator assigns a port (below), the handler builds the abstract autobind address from it, a leading NUL followed by five lowercase hexadecimal digits of the assigned number, and issues that rewritten bind on the guest's stack through record/replay, returning its answer directly and skipping the reachable and listener notes below.[c4][c15] A netlink bind whose address is at least a full sockaddr_nl with ID zero likewise gets an invented ID, the fixed base 0x4000_0000 with the assigned allocator number in its low bits, written into a stack copy that is bound through record/replay and returned directly; a netlink bind naming any other ID is not rewritten and not registered.[c5][c16] An Internet bind naming port zero asks the allocator for a port, writes the assigned number back into the guest's own address in guest memory, and remembers it as this call's candidate; a bind naming any other port only registers that port against the open file with the allocator — no conflict is decided there — with an optional warning under the analyze-networking configuration.[c6][c7] Every remaining family, and every named Unix bind, goes to the executor address unchanged. The final executor call, for all of these except the two directly-returned autobind forms, runs through record/replay with the (possibly rewritten) guest address — on the host kernel for the ptrace family and in the backend's Linux provider for KVM, whose own family and length answers are stated below (reverie-linuxemu/src/executor/socket.rs) — after the handler has read the Unix name the guest named, before the call, for its own bookkeeping.[c8] Where that call answers EADDRINUSE for a port this call invented, the handler releases the failed candidate, takes the next one from the allocator, rewrites the guest address again and retries, until a candidate binds, a candidate repeats, or the allocator reports the range full — a repeat means the allocator has cycled the whole range without a host-free port.[c8] A successful named Unix bind is then noted as reachable and under the name the guest named, and an abstract-name notice is emitted where that notice is configured; the autobind form skips both notes, and nothing else about the result is rewritten.[c9]

The deterministic allocator. Outside a DBT copied child, the allocator is run-wide state in the global tool: a cursor at the next candidate, the set of ports currently handed out or registered, and a map from each open file to the port it holds.[c17][c23][c24] It starts at the first port of the ephemeral range — the test-only override where the configuration sets one, otherwise the host's /proc/sys/net/ipv4/ip_local_port_range, re-read before each assignment — and each request takes the cursor's port where free, skipping handed-out ports with wraparound at the range end, inserts it in both ledgers and advances the cursor past the assignment, so the next request does not first re-offer the port just given out.[c25][c13][c10] A request that scans the whole inclusive range without finding a free port answers PortFull; a request for an already-named port simply inserts it, deciding no conflict, and a second request from one open file overwrites its map entry while its first port stays handed out, as the ledger gap below states.[c10][c11][c28] A port goes back only when the global state is told its open file's last reference went: the handler's own release helper issues that request, close and close-range issue it for a description's last reference, a replaced descriptor issues it at its replacement, an exec's dropped descriptors issue it, and the released-rights settlement issues it for a socket whose last reference was a copy in flight, while a fatal-signal settlement releases only copies in flight and not the dying table's own sockets — the global side then removes the port from both ledgers and leaves the cursor where it sits, so a freed port is re-offered only when the cursor comes back around.[c22][c14][c21][c12] A process exit is not among those releases for the table's own descriptors: letting a table go at its last holder's exit takes the queues of its sockets for release but keeps the descriptions' ports, as the code states an exiting process's sockets always have (G4).[c20][c21]

Interface fidelity. A named bind is the executor's: on the ptrace family the rewritten forms change only the piece the host kernel would have invented — the port-zero number, the unnamed Unix name, the zero netlink ID — except where the gaps below state otherwise, and the named address, its length, the descriptor and every success and error of the forwarded call itself pass through record/replay unchanged, so a filesystem Unix path is created or refused by the host filesystem, an explicit Internet port conflicts exactly as the host's existing binds decide, and getsockname afterwards reports the address the executor bound, deterministic number included; on KVM the provider answers the final call itself, refusing families beyond its set and short or long lengths before it reads the address (reverie-linuxemu/src/executor/socket.rs).[c6][c8][linux] The allocator's registration of an explicit port is bookkeeping for later invented assignments (an invented candidate skips it, subject to what the ledger keeps in G15), not a second conflict check: two guest sockets naming one explicit port receive the executor's own answer for the second, EADDRINUSE unless reuse options allow it, in the executor's order.[c11][linux] The fidelity differences Detcore itself makes are numbered as gaps below, not hidden, except the missing-pointer precedence difference in the refusal order, which has no gap: the guest-buffer write-back and its buffer-reuse consequence, the short-length full-structure read, the autobind errno and retry answers, the ledger leaks, and the uninvented forms each have their own gap. Two shape facts hold across them: the Unix autobind name is five hexadecimal digits of a port-range number, not the kernel's own autobind sequence, so its shape matches Linux's (a leading NUL and five lowercase hex digits) while its value is the allocator's, repeatable in schedule order; and the netlink ID is the fixed base with the allocator number in its low bits, above the task-ID space Linux derives its IDs from, so no guest task ID can collide with an invented one.[c15][c16][linux] The ConnectBind priority request orders the schedule to exercise races and can change which racing call runs first (G6); the reachable and named notes after a successful named Unix bind and the abstract-bind notice feed Detcore's own socket model, which later socket calls consult.[c3][c9]

Every refusal, in the order it is decided. Outside the three pre-dispatch takes below, Detcore has no deterministic refusal for this call (code facts in the Appendix): nothing else here is answered with a fixed errno under the fail-closed policy except the Fourth, Fifth and Seventh decisions below (inguest-engine/src/native/copied_action.rs).[c18] Its own decisions, in order, are these. First, on LiteInst in-guest alone, in a process that handles the virtual alarm signal, every bind gets EOPNOTSUPP from the phase gate before the handler, since this call sits in no admitted class.[c27] Second, a pathname Unix bind below a served directory is refused by name before dispatch — a fail-closed run ends and with the opt-out the answer is ENOENT — and a bind address naming a served entry outside the configured level is answered through a substituted path before dispatch (detcore/src/syscalls/files/descriptor_directory.rs, detcore/src/syscalls/files/procfs_levels.rs).[c29] Third, in the networking trace modes (--record-networking and --replay-networking), every Internet bind, every abstract Unix bind and every bare autobind ends the run under the policy-refusal exit before the handler, only a named filesystem Unix bind reaches the handler, and netlink sockets cannot be created in those modes at all.[c26] Fourth, a missing address pointer is EFAULT before the descriptor is looked up, where the kernel — which looks the descriptor up first — answers EBADF for a missing descriptor with a missing address and its not-a-socket and bad-length answers in their own places, and EFAULT only after the descriptor checks pass: for those combined cases Detcore's EFAULT precedes each kernel answer it displaces.[c3][linux] Fifth, a descriptor Detcore does not track, including one open in the kernel but unmodelled, fails from its open-file lookup with EBADF before the address family is read and before the executor runs, on the ptrace backend, KVM and LiteInst, while SaBRe and DBT discover such a descriptor instead; the kernel's own descriptor and not-a-socket answers therefore do not decide the call, though no call through a tracked socket reaches this decision.[c3] Sixth, reading the family, and reading the full protocol address for the rewritten families, fails as guest memory fails, before any allocator state changes for that family — for an Internet bind this full-structure read runs even where the guest's length is shorter than the structure, where the kernel refuses or accepts the short length without reading the rest, as the gap below states.[c3][c6][linux] Seventh, an allocator request that finds the whole ephemeral range handed out is EADDRINUSE before the executor call runs, for an invented port, an unnamed Unix bind and a zero netlink ID alike, decided by the allocator's ledger rather than the host's binds, where the kernel's Unix and netlink inventions give their own different answers as the gap below states.[c4][c5][c6][c10][linux] Last, every executor call then takes its executor's own order through record/replay — the host kernel's on the ptrace family: EBADF for a descriptor that is not open, the not-a-socket error for a descriptor that is not a socket, EFAULT for an address the executor cannot copy, then the protocol's own errors — its refusal of an already-bound socket or a short address, of a non-local Internet address, and of a privileged port or a protected filesystem path, and EADDRINUSE for an explicit port or Unix name already bound, including a port-zero Internet bind whose retry cycle found no host-free candidate; on KVM the provider checks length and family before the host's not-a-socket check (reverie-linuxemu/src/executor/socket.rs).[linux][c8] The precedence differences from the kernel are each decision above that the kernel has no counterpart for in that position, in the order stated: the guest-memory reads and the ledger decision likewise run before the kernel's descriptor and length checks they precede.[c3][c10][c8][linux]

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c2] In a plain run the record/replay path injects the forwarded call directly and the allocator needs no recording: its assignments are re-derived from the same sequence of allocator requests in schedule order, and the two autobind forms are re-derived the same way from the rewritten address they construct.[c4][c10] Under record, the record/replay path records the executor's answer for the (possibly rewritten) bind, and under replay it returns that answer without binding again, so a replayed port-zero bind reports success for the recorded assignment even if that port is now host-busy; the allocator requests themselves still run in replay, in the same order, keeping the cursor and ledgers in step for later calls the replay does execute where the replay host's ephemeral range matches the recording host's, and assigning different ports, written into guest memory and into the autobind copies, where it differs, as the gap below states.[c8][c10] What the subscription records for this handler is therefore the executor answer to the rewritten call, not the invention: the invention is deterministic state, the host conflict it may have hit is not, and the retry loop's candidates replay because each candidate comes from the same allocator sequence and each recorded executor answer is returned in turn.[c8]

Known gaps

  • G1 (unimplemented; DBT copied child only): in a DBT copied child — the window between a vfork and the exec of the child's next program, where no Detcore tool runs — this call runs natively in the kernel, in fail-closed runs and under --allow-unsupported-syscalls alike: it is on the copied child's acknowledged-escape list, is not in the deterministic-refusal set (which by construction excludes emulated calls like this one, the Unix autobind emulation named there), and the copied-child gate therefore lets it through to the host (inguest-engine/src/native/copied_action.rs).[c18] On the ptrace backend (including e9patch preprocessing, which is not a backend), KVM, SaBRe and LiteInst the same call reaches the handler above except where the trace and phase takes below own it first. A port-zero, unnamed-Unix or zero-ID bind in that window receives the host's invented port, name or ID, and registers nothing with the allocator, so a guest whose invented address in that window must repeat must avoid the copied-child path; there is no fallback inside the call on DBT.
  • G2 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a named bind is still the host's object outside the invented pieces on the ptrace family: the filesystem path a Unix bind creates, the host binds an explicit port conflicts with, and the host TIME_WAIT state a retry steps around are whatever the host does when the forwarded call runs, so a filesystem or network namespace that changes under the run, or differs between hosts, changes whether the bind succeeds, and Hermit makes this call repeatable only so far as that namespace repeats; on KVM the provider gives the final answer itself, as the KVM gap below states (reverie-linuxemu/src/executor/socket.rs).[c8][linux]
  • G3 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the ephemeral range itself is read from the host — /proc/sys/net/ipv4/ip_local_port_range at startup and again before each assignment, unless a test override replaces it — so the first invented port, and therefore the whole assignment sequence, the Unix autobind names and the netlink IDs derived from it, repeat across runs on one host configuration but can differ on a host whose range differs, with no guest-visible indication of which range was used.[c13][c25][c10] A guest that must name its port must bind it explicitly; there is no fixed range inside the call.
  • G4 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a port held by a socket whose process exits without closing it is not returned to the allocator by the exit: letting the descriptor table go at its last holder's exit keeps the descriptions' ports, and only a last-reference close, a close-range, a descriptor replacement, an exec's dropped descriptors, or a copy-in-flight settlement releases one, a fatal-signal settlement releasing only copies in flight and not the dying table's own sockets — so a run of short-lived processes that bind port zero and exit steadily consumes the ledger, and later invented binds can answer EADDRINUSE from allocator exhaustion while the host range stands empty.[c20][c21][c14] A guest in that case must close its sockets before exit; there is no exit-time fallback inside the call.
  • G5 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): only the three invented pieces are determinized. An explicit netlink ID is neither rewritten nor registered, and every other family — a named Unix bind included — is forwarded with no allocator record at all, so collisions among explicit netlink IDs and the success of any other family's bind are decided entirely by host state the allocator never saw, and a later invented assignment knows nothing of them beyond what its own executor retry observes.[c5][c8] A guest that must coordinate explicit IDs must coordinate them itself; the allocator coordinates invented pieces only.
  • G6 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT, SaBRe, LiteInst): whether the ConnectBind priority request changes any observable outcome — which of two racing binds runs first where the schedule would otherwise order them — is claimed from the handler and scheduler code, not from a measured run at the pin: no guest at the pin races a bind against a connect under that heuristic across the ptrace backend (including e9patch preprocessing), KVM, DBT, SaBRe and LiteInst.[c3]
  • G7 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT, SaBRe, LiteInst): guest program bind_getsockname under tests/c exercises an abstract named Unix bind read back by getsockname and a rebind refusal as text, allocator unit coverage exercises assignment, release and exhaustion through the global RPC, and no machine-verified coverage at the pin distinguishes the invented port sequence, the Unix autobind name, the netlink ID, or the host-busy retry across the ptrace backend (including e9patch preprocessing), KVM, DBT, SaBRe and LiteInst; each is therefore claimed from the handler and allocator code above, not from a measured run.[c6][c10]
  • G8 (unmeasured; ptrace record and replay): under replay the allocator still assigns and the guest address is still rewritten, but the recorded executor answer is returned without binding, so whether a replayed run's later getsockname, connect or accept observes the same address the recording bound — where the recorded bind's port has since been taken on the replay host — is claimed from the record/replay path, not measured at the pin; the recording side's answer is repeated, the host socket it names may not exist.[c8]
  • G9 (unimplemented; ptrace, KVM, LiteInst in the networking trace modes): in the networking trace modes (--record-networking and --replay-networking, refused at launch for executable-selected backends, and e9patch preprocessing cannot run them either) every Internet bind, every abstract Unix bind and every bare autobind ends the run under the policy-refusal exit before this handler, and netlink sockets cannot be created there at all, where Linux would bind or refuse with its own answer, so a guest in those modes has no bind through this handler for those forms; only a named filesystem Unix bind reaches it.[c26]
  • G10 (unimplemented; LiteInst in-guest): on LiteInst in-guest alone, in a process that handles the virtual alarm signal, every bind gets EOPNOTSUPP from the phase gate before this handler, where Linux would bind or refuse with its own answer, so a guest in that process has no bind through this handler; there is no admitted form inside the call.[c27]
  • G11 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a port-zero Internet bind writes each candidate into the guest's own address buffer and leaves the last candidate there after a failed bind, where Linux never writes the bind address back, so a guest that reuses that buffer for another port-zero bind names the first port explicitly, takes no retry, and gets the executor's conflict answer or a shared reuse port where Linux gives each call a fresh port; a guest in that loop must rewrite its buffer, and there is no buffer-preserving form inside the call.[c6][c8][linux]
  • G12 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the Internet branches read the full protocol structure from the guest address before the executor can refuse or accept a short length, so a valid short address at the end of a mapped page can fault where Linux accepts it and a port-zero bind writes the whole structure back past the declared length, rewriting bytes the guest never offered including the port bytes for the shortest lengths; a guest in those cases has no length-faithful form inside the call.[c6][c7][linux]
  • G13 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the autobind form returns before the reachable and listener notes, so an autobound socket is never marked reachable though the reachability contract names autobind (detcore/src/syscalls/scm_rights.rs) and its queue is still treated as holding every message, and never registered as a listener, where a named bind gets both notes; a guest whose autobound socket must be found that way has no noted form inside the call.[c4][c9]
  • G14 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the Unix and netlink inventions answer differently from the kernel per case: Unix exhaustion gives EADDRINUSE here and ENOSPC in Linux; an already-bound Unix autobind gives EINVAL here where Linux succeeds as a no-op; a taken invented name or ID gives EADDRINUSE with no retry here where Linux retries; netlink exhaustion retries without end in Linux — so a guest in those cases meets Detcore's answer and has no kernel-faithful form inside the call.[c4][c5][linux]
  • G15 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a failed bind keeps its invented or registered port, a second request from one open file leaves its first port handed out for the rest of the run, and releasing one of two holders of one explicit port frees it while the other still holds it, each able to exhaust the ledger while the host range stands free with the same symptom as the exit case above from a different cause; a guest in those cases has no leak-free form inside the call.[c28][c12]
  • G16 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): three forms are not invented here as Linux invents: an AF_UNSPEC Internet address the kernel treats as its Internet form including its port-zero search goes forward unchanged and receives the kernel's random port, an IP_BIND_ADDRESS_NO_PORT request still receives and binds an allocator port so later address answers change, and the allocator ignores the host's ip_local_reserved_ports list the kernel's search skips, so a guest in those cases receives a host-chosen or reserved port the run did not schedule; there is no determinized form inside the call.[c6][c10][linux]
  • G17 (unimplemented; record and replay): record and replay re-read the ephemeral range from the replay host at every assignment, so a replay whose host range differs assigns different ports and writes them into guest memory and into the autobind copies while returning the recorded answers, silently differing from the recording; a guest that must replay identically needs an equal range, and there is no range-pinned form inside the call (hermit-cli/src/metadata.rs, hermit-replay/src/replayer.rs).[c8][c10]
  • G18 (unimplemented; ptrace, KVM, LiteInst): a pathname Unix bind below a served directory is refused by name before dispatch — a fail-closed run ends and with the opt-out the answer is ENOENT — and a bind address naming a served entry outside the configured level is answered through a substituted path before dispatch, each where the kernel's descriptor order would decide the call; placeholders are served only where the tool does not share the guest's descriptor table and not under record and replay; a guest in those cases has no forwarded form inside the call (detcore/src/syscalls/files/descriptor_directory.rs, detcore/src/syscalls/files/procfs_levels.rs).[c29]
  • G19 (unimplemented; KVM): the provider answers EAFNOSUPPORT for any family outside AF_INET, AF_INET6, AF_UNIX and AF_NETLINK, including an Internet bind with AF_UNSPEC and the any-address which Linux accepts, and EINVAL for lengths under two or over one hundred twenty-eight, checked before the address is read (reverie-linuxemu/src/executor/socket.rs), so a guest on KVM meets the provider's family and length answers and has no host-kernel form there.[c8]
  • G20 (unimplemented; ptrace, KVM, LiteInst; SaBRe and DBT discover the descriptor): a descriptor Detcore does not track, including one open in the kernel but unmodelled, fails with EBADF from its open-file lookup before the address family is read and before the executor runs on the ptrace backend, KVM and LiteInst, where Linux would bind a socket it does not model or give the not-a-socket answer for a non-socket, so a guest holding such a descriptor cannot bind it on those backends; SaBRe and DBT discover such a descriptor instead, and there is no tracked form inside the call on the others.[c3][linux]
