write (1)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-20 at 403e350e9e82

In short

Natively, write copies up to the requested count from a guest buffer to the object behind a descriptor and returns how many bytes it copied, so how much room a pipe or socket had, whether a reader was present, and when the call waited all show in the answer. Outside a DBT copied child, which runs it natively, Hermit forwards ordinary descriptors to the host kernel on the ptrace family and to the backend's own Linux provider on KVM, runs the call inside its serialized schedule, answers a timer-slack descriptor from its own model, completes a logically blocking write to a pipe it made physically nonblocking by retrying the unwritten remainder in guest turns, and retries the remaining kinds in the same folded way whenever deterministic I/O is on, which is the default in a plain run. The sibling call writev shares parts of this handler family and keeps its own page; it is cross-linked here and is not checked on this page. Known gaps: 16.

Determinism strategy

What is nondeterministic natively. write takes the descriptor's file, checks it can be written, checks the source, and copies toward the current position, advancing that position by what it copied.[linux] How much it copies on one call is the host's answer: a pipe or socket takes less than asked when only that much room had arrived, a pipe with no reader fails, and a blocking descriptor waits until room or a reader arrives, so arrival timing decides both the count and when the call returns.[linux] For a pipe, the kernel copies in page-sized pieces and waits for room when full, which is what makes a small write indivisible and a large one interruptible part-way.[linux]

What Hermit does. Outside a DBT copied child, Detcore determinizes write by handling it with the shared typed handler for the write family: classification places the entry with the determinized calls, and typed dispatch notes the send for the descriptor before and after the handler runs.[c1][c2] Two takes run before that dispatch where they apply: on LiteInst in-guest alone, in a process that handles the virtual alarm signal, a phase gate admits only a write to container standard output or error, a memory descriptor, or a safe rendered snapshot and refuses a pipe write and every other write before the handler runs (see the refusal order below);[c30][c31] and in the networking trace modes (--record-networking and --replay-networking) a write on a recorded channel socket is taken by the trace path before dispatch.[c39] A rendered placeholder opened for writing is likewise answered before dispatch from its own rendered code, as a second modeled answer beside timer-slack.[c32] Inside the handler, a kernel-run entry the in-guest delivery gate cannot run is refused first among handler refusals, then a timer-slack binding is answered and returns, each in the order stated below.[c3] A nonzero write to a FIFO whose other end a guest may hold is first offered the FIFO polling treatment: when the host's pipe-max-size is below two pages the run ends before anything else and nothing is shrunk; otherwise a larger FIFO is shrunk to the pinned two-page capacity and made physically nonblocking where the poll applies; a zero-count write skips that offer.[c7][c33] The ptrace family is every backend except KVM (ptrace including e9patch preprocessing, DBT, SaBRe and LiteInst). The handler then reads the descriptor's kind, physical and logical blocking state, open-file identity, write resource and raw inode from its model — an unknown descriptor fails here, before any byte moves — bumps the file's virtual modification time where metadata is virtualized, and takes the write grant on the open-file resource before any bytes move, so writes to one description run one guest turn at a time in schedule order; a write to inherited container output with the alarm signal handled records a determinism loss at that grant only where an alarm is due and still runs.[c7][c20] What happens next is chosen by the descriptor's physical state and kind. A physically nonblocking pipe whose guest view is blocking goes through the blocking-pipe completion below. Any other physically nonblocking pipe, socket or event descriptor goes through the nonblockable path with three outcomes: where the peer is inside the run the call retries in guest turns, where the peer is outside a plain run still polls in guest turns on host-peer readiness while only record and replay runs it as one blocking forwarded call, and a descriptor the guest set nonblocking runs once with no retry in turns.[c8][c13][c14][c34] In a sequentialized plain run every socket is made physically nonblocking, so a guest-blocking socket write takes that same retry path and returns its first non-blocking result, a short count included, with no folded completion and no deterministic-I/O folding.[c35][c36][c37] Every remaining descriptor — a regular file, a physically blocking pipe, and every other kind — takes the single forwarded answer through record/replay, on the host kernel for the ptrace family and on the backend's Linux provider for KVM (reverie-linuxemu/src/executor/read_write.rs, reverie-linuxemu/src/executor/dispatch.rs, reverie-kvm/src/runtime.rs), folded by the deterministic-I/O loop below only where that mode is on.[c8] A timer-slack descriptor never reaches any of this: Detcore parses the written decimal itself, stores it as the target's slack (the default where the value is zero), and returns the full count with no kernel write.[c4][c5][c6]

Interface fidelity. The count, the bytes and the position advance are the executor's for every descriptor Detcore forwards — the host kernel on the ptrace family and the backend's Linux provider on KVM (reverie-linuxemu/src/executor/read_write.rs) — because it copies with the guest's own call and returns its count unchanged outside the modeled answers above and the two folded loops below.[c15][linux] The modeled answers are the timer-slack parse and the rendered-placeholder answer, each as stated above.[c4][c32] The blocking-pipe completion is the first folded loop: Hermit's physical nonblocking flag is its own scheduler mechanism, so exposing the first short forwarded answer would hand the guest a count Linux's blocking call would not have returned yet; the helper instead retries the unwritten suffix at the advanced buffer until the capped request completes, a signal ends it with the bytes already written (or the interrupt error where there are none), or a real error ends it the same way, returning the folded total as one call.[c9][c11][c12] Its request is capped the way the kernel caps one copy, and a zero-length request delegates to the nonblockable path and returns the executor's null-write answer.[c9][linux] The deterministic-I/O loop is the second: with that mode enabled, a remaining descriptor is written again at the advanced buffer until the request fills or a call returns zero, and an error after some bytes copied returns those bytes instead of the error — exactly the call sequence a guest that loops on short writes would make, folded into one call.[c8][c16] It does not run for the pipe or event kinds above and never folds a physically nonblocking socket write, which returns its first retry result as stated above (a physically blocking socket without sequentialized threads can take this loop), and without the mode a short copy is returned as the executor gave it.[c8][c13][c36] There are no flags or options on this call to honor or coalesce; its only arguments are the descriptor, the source and the count, and a missing source on the modeled answer is EFAULT where the forwarded call's own copy gives the same answer for a forwarded one.[c5][linux]

Every refusal, in the order it is decided. First, on LiteInst in-guest alone, in a process that handles the virtual alarm signal, the phase gate refuses every write it does not admit — a pipe write explicitly, and a regular-file, socket, event-descriptor and unmodelled-descriptor write among them — with EOPNOTSUPP before any dispatch; only container standard output or error, a memory descriptor, and a safe rendered snapshot reach the handler in that process.[c30][c31] Second, in the networking trace modes (--record-networking and --replay-networking), a write on a recorded channel socket is taken by the trace path before dispatch, and a broken-pipe error there without the no-signal flag, which this call never sets, ends the run.[c39] Third, under the in-guest delivery gate only, the entry checkpoint decides before anything else in the handler: a fatal end becomes the interrupt error at the return where the process dies and the guest never sees a restart value, a caught end that resolves to caught is the stopping refusal that ends the run, and a thread state that cannot be read (detcore/src/syscalls/helpers.rs) also ends the run, so no modification-time bump is left behind by a refused entry; in the caught case Linux runs the handler first and the process survives if the handler changes the signal's disposition or mask; with the gate off there is no such refusal.[c3][c38] Fourth, on a timer-slack descriptor, a descriptor that cannot write is EBADF, then a missing source is EFAULT, then a non-decimal value is EINVAL and an overflowing one ERANGE, then a target that has exited or been recycled is ESRCH and a target that is not the caller is EPERM, then a count the return cannot hold is EINVAL, with the cross-task permission refused unconditionally as a stated intentional divergence below.[c4][c5][c6][c23] Fifth, a descriptor open in the kernel but unmodelled fails from the model lookup itself before the grant with EBADF, where the kernel would write, on the ptrace backend, KVM and LiteInst, while the remaining backends discover such a descriptor instead, as the same divergence the ioctl page carries as G19; a known descriptor takes its grant, which waits rather than fails.[c7] Sixth, a nonzero write to a FIFO when the host's pipe-max-size is below two pages ends the run without a policy gate before anything is shrunk, as stated above.[c33] Seventh, inside the blocking-pipe completion, a descriptor replaced or closed after the call waited is refused instead of writing the suffix into an unrelated object: with bytes already written the folded count is returned, with none the refusal is EOPNOTSUPP under --allow-unsupported-syscalls and otherwise a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit, ends on DBT through its runtime exit path, and on SaBRe ends only the refusing process so the run can wait on stranded, with no strand exception giving EOPNOTSUPP outside the opt-out on any backend.[c10][c19] Last, every forwarded call then takes its executor's own order — the kernel's on the ptrace family and the provider's on KVM (reverie-linuxemu/src/executor/read_write.rs, reverie-linuxemu/src/executor/refusal.rs): EBADF for a descriptor that cannot be written, EINVAL where the file cannot write at all, EFAULT for a bad source, then the range check's own errors, then the file's own errors including EAGAIN on a nonblocking descriptor with no room and EPIPE with its signal on a pipe whose readers have gone.[linux][c39] The precedence differences from the kernel are each refusal above that the kernel has no counterpart for, in the order stated; the timer-slack refusal by construction only applies through a descriptor Detcore bound as timer-slack, and the replaced-descriptor refusal only after a first attempt the executor already accepted.[c38][c10][linux]

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c2] In a plain run the forwarded branches inject the forwarded call directly and the modeled branch (timer-slack) needs no recording because it is re-derived from model state.[c15][c4] The subscription's output side is exact, and it is not a re-run: while recording, the recorder injects the guest's own write once, captures its result together with the output endpoint, offset and signal side effects, and stores that as the call's event (hermit-record/src/recorder/fs.rs).[c15] While replaying, the replayer does not inject the write again against the live descriptor except for an event descriptor, whose kernel counter is advanced by re-injecting with an assertion that panics where the replayed counter diverges; for a regular file in the replay root it re-reads the recorded count of bytes from the guest's own buffer at replay time and writes them at the recorded offset in the replay root, for a captured output it re-emits those same guest-buffer bytes to the captured endpoint, for a shared-mapping backing it writes through that backing, and for every other descriptor, internal pipes and sockets among them, it does nothing at all, returning the recorded count or error (and replaying a recorded SIGPIPE where the recording made one) without touching the host sink again (hermit-replay/src/replayer/fs.rs).[c15] Replay therefore repeats the recorded short count and the recorded error even if the sink has since gained room or a reader, and the bytes it re-emits are the bytes in guest memory when replay reaches the call, not bytes stored in the recording. Only the deterministic-I/O loop is off under record and replay; the blocking-pipe completion runs there with each attempt recorded and replayed (hermit-cli/src/bin/hermit/run.rs, hermit-cli/src/metadata.rs).[c8] A write to a socket Detcore keeps only in the log is served from the log on the blocking path during replay rather than re-run.[c13][c14][c17]

Known gaps

  • G1 (unimplemented; DBT copied child only): in a DBT copied child — the window between a vfork and the exec of the child's next program, where no Detcore tool runs — this call runs natively in the kernel, in fail-closed runs and under --allow-unsupported-syscalls alike: it is on the copied child's acknowledged-escape list, is not in the deterministic-refusal set (which by construction excludes ordinary forwarded calls like this one), and the copied-child gate therefore lets it through to the host (inguest-engine/src/native/copied_action.rs).[c29] On the ptrace backend (including e9patch preprocessing, which is not a backend), KVM, SaBRe and LiteInst the same call reaches the handler above except where the phase gate below refuses it first. A guest whose writes in that window must be serialized or modeled must avoid the copied-child path; there is no fallback inside the call on DBT.
  • G2 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): an ordinary file, pipe or socket is still the host's object outside the modeled answers: its room, its reader, and whether it accepts the write at all are whatever the host does when the forwarded call runs, so a filesystem or peer that changes under the run, or differs between hosts, changes the count and the bytes that land, and Hermit makes this call repeatable only so far as that sink repeats. On the ptrace backend (including e9patch preprocessing), DBT outside a copied child, SaBRe and LiteInst the executor is the host kernel through the same handler; on KVM the executor is the backend's Linux provider instead, whose own answers are a gap below (reverie-linuxemu/src/executor/read_write.rs, reverie-kvm/src/runtime.rs).[c8][c15]
  • G3 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the folded completion of a short write runs for a logically blocking pipe only through the blocking-pipe helper, and for the remaining kinds only with deterministic I/O enabled; that mode is on by default in a plain run and always under the strict policy, and off only with the explicit opt-out and under record and replay (the run configuration turns it on unless opted out and the record and replay configuration turns it off, hermit-cli/src/bin/hermit/run.rs and hermit-cli/src/metadata.rs). Without it a regular file's or physically blocking descriptor's single forwarded answer stands, and on every backend a short copy is returned as the executor gave it, so a guest that does not loop on short writes sees host room timing in its counts.[c8][c9]
  • G4 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a blocking pipe write whose descriptor is replaced or closed while it waits does not keep writing to the original open file as the kernel does inside a blocking call: with no bytes written it is refused as stated above — a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit, ends on DBT through its runtime exit path, and on SaBRe ends only the refusing process so the run can wait on stranded — where Linux would complete or fail against the original description, and a guest in that case must keep the descriptor stable across the wait; there is no retained-descriptor fallback inside the call.[c10]
  • G5 (unimplemented; LiteInst/in-guest with the delivery gate only): where the entry checkpoint ends fatally the process dies at the return and the guest never sees a restart value, and where a caught end resolves to caught the run ends under the stopping refusal, each where Linux would deliver the signal first (the process surviving if the handler changes the disposition or mask); a guest in that case has no fallback inside the call; with the gate off, and on the ptrace backend (including e9patch preprocessing), KVM, DBT outside a copied child and SaBRe, the entry runs as stated above.[c38]
  • G6 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst, where metadata is virtualized): the virtual modification-time bump runs before the write's outcome is known, so a write that then fails before any byte could move — a descriptor that cannot write among them — and a pipe write that moves no byte still advance the file's virtual time, where the kernel advances a regular file's time before its copy and a pipe's time only for bytes actually moved; a following metadata answer therefore reports a change no byte caused in those pre-copy and pipe cases, on every backend that virtualizes metadata through the same handler.[c7][c20][linux] A guest that must not see the bump must not fail the write in those cases; there is no rollback inside the call.
  • G7 (by design; ptrace record and replay): replay does not re-issue the write against a live ordinary descriptor other than the event, replay-root regular-file, captured-output and shared-backing cases above, internal pipes and sockets included: the recorded count returns and the host sink never receives the bytes in the replay run, so a peer or file outside the replay root that recording wrote to is not written again; a guest that needs the replay itself to reach that sink has no fallback inside the call (hermit-replay/src/replayer/fs.rs).[c15]
  • G8 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): whether a blocking pipe or event write waits in guest turns or as one blocking forwarded call depends on whether the descriptor is physically nonblocking, whether the peer is inside the run and on thread sequentialization, and under record/replay an outside peer always takes the blocking form, but no measurement here pins whether an outside reader that never reads leaves the same observable wait, or the same interrupted-write answer, across those configurations; socket counts in that comparison are the short-count gap below, not an equivalence.[c13][c14]
  • G9 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): guest programs file_io_roundtrip, pipe_multiwriter_ordering and writev_determinism under tests/c exercise a write-then-read-back sequence, concurrent pipe writers and the vectored sibling as text, and no machine-verified coverage at the pin distinguishes the blocking-pipe folded count, the deterministic-I/O folded count, the timer-slack answer or the replay re-emission across the ptrace backend (including e9patch preprocessing), KVM, DBT, SaBRe and LiteInst; each is therefore claimed from the handler code above, not from a measured run.[c8][c9][c4]
  • G10 (unimplemented; every backend where sockets are physically nonblocking): a guest-blocking stream-socket write in a sequentialized plain run goes to a socket Detcore made physically nonblocking and returns its first non-blocking result, a short count included, where Linux loops until every byte is queued, including internal socketpairs and internal sockets under record and replay, and the deterministic-I/O loop never folds it, so a guest that writes more than the send buffer must loop itself; there is no folded socket form inside the call.[c35][c36][c37]
  • G11 (unimplemented; LiteInst in-guest): on LiteInst in-guest alone, in a process that handles the virtual alarm signal, every write the phase gate does not admit — a pipe write explicitly, and a regular-file, socket, event-descriptor and unmodelled-descriptor write among them — gets EOPNOTSUPP before the handler runs, so a guest in that process must write only to an admitted descriptor; there is no handler fallback in that process.[c30][c31]
  • G12 (unimplemented; networking trace modes): in the networking trace modes (--record-networking and --replay-networking) a write on a recorded channel socket never reaches this handler: in record mode the trace path sends to the host socket and completes a blocking write, in replay it writes to the trace and not the host socket, and a broken-pipe error there without the no-signal flag ends the run, so a guest in replay mode writes to the trace only; outside those modes this gap does not apply.[c39]
  • G13 (unimplemented; KVM): on KVM alone, one forwarded write is capped well below the kernel's cap (reverie-linuxemu/src/executor/read_write.rs), captured output is always the provider's with no host write and EFBIG when full, and a zero-count write returns early except on sockets, so a large regular-file write with deterministic I/O off can return short on KVM alone and a guest that must move more in one call must loop; no larger single-call form exists on KVM.[c8]
  • G14 (unimplemented; ptrace, KVM, LiteInst): a descriptor open in the kernel but unmodelled fails with EBADF from the model lookup on the ptrace backend, KVM and LiteInst, where Linux would write, so a guest holding such a received descriptor cannot write it there; the remaining backends discover the descriptor instead, as the same divergence the ioctl page carries as G19.[c7]
  • G15 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a nonzero write to a FIFO when the host's pipe-max-size is below two pages ends the run without a policy gate before anything is shrunk, where Linux would write or wait, so a guest in that host configuration has no write through that FIFO; there is no smaller-pipe fallback inside the call.[c33]
  • G16 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a timer-slack write naming another task is refused unconditionally, where the kernel allows it with the scheduling capability and clears the slack for the real-time classes, as an intentional divergence the code states it does not expose, so a guest that sets another task's slack has no form of this call that succeeds.[c23]
