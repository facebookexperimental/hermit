recvmsg (47)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-20 at 403e350e9e82

In short

Natively, recvmsg receives one message with its address, data and ancillary control data, and can wait for a sender whose timing is host state, install host-chosen descriptor numbers over SCM_RIGHTS, and stamp host wall-clock socket timestamps. On every backend that runs the Detcore tool except KVM, Hermit forwards the call itself to the kernel; on KVM the reverie-linuxemu provider (executor/socket.rs in the Reverie tree, named here as text evidence, not as a checked citation) answers the call instead, with its own control-data, flag, error-order and refusal behaviour (G9), but Detcore takes over the wait and the host-varying pieces: a logically blocking receive on a physically nonblocking socket is retried in scheduler turns until data, a signal, read shutdown or the socket's receive timeout ends it (the read-shutdown finish does not apply under record and replay, G15), the descriptors a receive installs are recorded into Detcore's table under the numbers the kernel gave them — or, on KVM, the provider's own lowest-free numbers — (or discovered, where the tool shares the guest's table), and socket timestamps in the control bytes the receive actually wrote are rewritten to logical time; in a DBT copied child the call never runs natively at all: it is refused, strictly by ending the run and otherwise with EPERM, and the sibling calls sendmsg, recvmmsg, sendmmsg, sendto and recvfrom keep their own pages; they are cross-linked here as the message-family context and are not checked on this page. Known gaps: 19.

Determinism strategy

What is nondeterministic natively. Linux first refuses MSG_CMSG_COMPAT with EINVAL, then looks the descriptor up (EBADF, then not-a-socket), copies the message header in, and only then receives, so descriptor and copy errors precede any wait.[linux] The receive itself waits as the descriptor and flags allow, fills the iovecs, name and control buffer, installs any SCM_RIGHTS descriptors at the receiver's lowest free numbers with close-on-exec only under MSG_CMSG_CLOEXEC, releases the ones that do not fit under MSG_CTRUNC, and writes back msg_controllen, msg_flags and the name length after the control messages; Linux likewise installs a pidfd for SCM_PIDFD at the receiver's lowest free number, a second kernel installer of descriptors (G16).[linux] Those installed numbers, the sender credentials in SCM_CREDENTIALS, and SCM_TIMESTAMP/SCM_TIMESTAMPNS/SCM_TIMESTAMPING values are all chosen from host state the guest did not supply: the numbers from the receiver's host descriptor table at that instant, the credentials from the host sender, the timestamps from the host clock.[linux]

What Hermit does. Detcore determinizes recvmsg by handling it with the shared typed handler for the socket family: classification places the entry with the determinized calls, and typed dispatch reaches the handler.[c1][c2] The handler first captures the receive geometry — the header, iovec, name and control extents as they stand at entry, and again before each retry attempt, because a sibling may change them while an earlier attempt waits — then receives one message, and afterwards, on success, works only from the control bytes Linux reports writing at the control buffer named before the call.[c3][c16] From those bytes it records the descriptors the receive delivered over SCM_RIGHTS, classifies them, drops any received pipe's SIGALRM tracking, and — only with virtual time and outside record and replay — refreshes the lock model for the descriptors delivered or recorded; a recorded descriptor's close-on-exec comes from its F_GETFD fact, and MSG_CMSG_CLOEXEC from the original flags is kept only for a descriptor listed without its facts.[c3] A receive error is noted against the socket before it propagates, and no descriptor work runs for it.[c3] On a NETLINK_SOCK_DIAG or route socket under metadata virtualization the handler instead snapshots the iovec segments before the receive and canonicalizes the supported host socket identities in the payload afterwards; that path receives through the same socket-receive helper as the plain path.[c23][c14]

The blocking wait, exactly. Whether the call may wait is decided from the descriptor's virtual and physical nonblocking state together with the call's own flags.[c9] Detcore keeps guest sockets physically nonblocking, so a logically blocking receive is not passed to the kernel as a blocking call: it takes the nonblockize-and-retry path, while a guest-nonblocking descriptor, a MSG_DONTWAIT call, and a MSG_ERRQUEUE receive on a modelled protocol whose error queue never waits each run exactly once, as Linux runs them.[c9][c7] The retry path first files a scheduler resource request for internal I/O polling and is admitted turn by turn; each attempt is the guest's own call unchanged — the nonblocking conversion for a socket call is the identity, on the stated expectation that the socket is already physically nonblocking — executed once, and a result of EAGAIN or EWOULDBLOCK is classified would-have-blocked and does not reach the guest.[c6][c7][c8] Between attempts the loop re-reads the geometry and the entry-time copy of the call's memory, checks whether the socket's read side was shut down by the guest itself (which, outside record and replay, finishes the call with one blocking run of the guest's call, returning Linux's answer, normally a zero-length return; under record and replay that finish is skipped and the receive never finishes, G15), checks an already-expired receive timeout, checks whether a signal ends the wait, and otherwise files the next polling request, so the thread waits in the scheduler's order rather than in the kernel and other guest threads run deterministically in between.[c8][c20][c15] The wait ends with the first of: an attempt that transfers a message (its result, address, data and control bytes are the kernel's); the socket's SO_RCVTIMEO, snapshotted once at entry on Detcore's model of the descriptor, expiring in logical time, which answers EAGAIN — an immediate timeout answers after the first would-block attempt, before any signal is consulted; a signal that would be delivered, which answers the entry-snapshotted interrupt errno (ERESTARTSYS for an untimed wait, EINTR for a finitely timed one, settled by the guest's handler disposition on resume); or the read-shutdown finish above.[c19][c20] Without sequentialized threads, on a physically blocking descriptor, or for a non-internal descriptor under record/replay, the call does not poll: it runs once as a blocking call outside the caller's turn, and other threads may run before the kernel reads its arguments — that is the background path, whose consequences for ancillary data are G4.[c6][c19] A descriptor Detcore cannot classify also takes that blocking path, deliberately, so the kernel and not Detcore's metadata lookup decides the call's errno.[c6]

Ancillary data: descriptors. Except on KVM, the kernel, not Detcore, installs received descriptors, so the numbers a guest sees are the kernel's lowest-free numbers at the receiving instant — deterministic only because the receiving table's history is itself schedule-ordered under sequentialized threads; on KVM the reverie-linuxemu provider installs rights at the lowest free numbers of its own guest table (G9).[linux][c22] What Detcore adds is a model of those numbers before any later call can use them, in one of three modes by backend shape: where the tool shares the guest's descriptor table (SaBRe and DBT) it records none and discovers each descriptor when a call first names it, marking any delivered inotify instance whose host nonblocking state may be the tool's own; without sequentialized threads it records none, at debug level only; everywhere else (ptrace including e9patch preprocessing, KVM and LiteInst) it records each delivered descriptor as the receive returns, from the kernel's own facts for that number (F_GETFD, F_GETFL, fstat, and the descriptor link for anonymous inodes), taken through the recording under record/replay — LiteInst records descriptors in this way, it does not discover them.[c22][c10][c11] A descriptor recorded for a file it cannot join takes the host's status flags, O_NONBLOCK included (G17), and a received per-process record file that joins nothing has every later read and seek refused by name (G18). A recorded descriptor that matches, by device and inode, an open file the sender's Detcore table queued on the socket at its send joins that modeled open file as dup would — sharing status flags, position and lock identity, a peek leaving the queued copy in flight — checked before the anonymous-inode refusal, so a received eventfd can join the sender's eventfd; one that joins is not returned as a new file for the lock refresh.[c21][c11] Descriptors that fit no modeled file are recorded as open files of their own, except each anonymous inode other than an inotify instance, each number that already has a record, and each whose facts cannot be taken, all left unrecorded and named in a warning (G5).[c11][c21] The guest's result is never changed by any of this recording; the one exception is a fail-closed run ending, below.[c11]

Ancillary data: timestamps, credentials, everything else. Only socket timestamps are rewritten, and only where time is virtualized and the message names a non-empty control buffer: the handler validates the control region before consuming a datagram, receives, observes the receive in logical time, then rewrites, in exactly the control bytes Linux reports writing, every SCM_TIMESTAMP to that logical time as a timeval, every SCM_TIMESTAMPNS as a timespec, and every populated SCM_TIMESTAMPING slot to it while a zero slot stays zero; bytes past the written length are the guest's own and are never parsed or rewritten.[c4][c5][c12][c13] Where time is not virtualized, or the message has no control buffer, the receive runs without that snapshot and rewrite, and a timestamp the kernel wrote is the host's (G6).[c4] Except on KVM, SCM_CREDENTIALS and every other control message are forwarded as the kernel wrote them: Detcore parses control data only to find SCM_RIGHTS descriptors and timestamp messages, and canonicalizes neither the sender's host pid/uid/gid nor any other ancillary payload (G3). On KVM the provider keeps only SCM_RIGHTS and the timestamp types and strips the rest, SCM_CREDENTIALS and SCM_PIDFD included (G9).[c11][c12] Without metadata virtualization a sock-diag payload likewise keeps its host identities; with it, only the supported fields are canonicalized, fail-open and without resizing.[c23]

`MSG_*` flags: their fates. Except on KVM, no flag is stripped, added or emulated by the handler: the typed call, flags included, is what each kernel attempt runs; on KVM the provider runs every host receive with MSG_DONTWAIT | MSG_CMSG_CLOEXEC, clears MSG_CMSG_CLOEXEC from the returned msg_flags when the guest did not ask for it, and adds MSG_CTRUNC (G9).[c7] Four flags additionally steer Detcore around that attempt. MSG_DONTWAIT makes the call run once even on a descriptor the guest left blocking, and its EAGAIN is then the guest's answer, as on Linux.[c9][c7] MSG_PEEK is read twice by Detcore — to leave a queued SCM_RIGHTS copy in flight rather than releasing it, and to note the receipt — while the kernel attempt itself decides peeking.[c3][c21] A recorded descriptor's close-on-exec comes from its F_GETFD fact; MSG_CMSG_CLOEXEC read from the original call is kept only for a descriptor listed without its facts, and the kernel's installation under it is otherwise unchanged.[c3][linux] MSG_ERRQUEUE marks the call an error-queue read, which runs once on a modelled protocol whose error queue never waits, and otherwise waits like any receive.[c7][c9] MSG_WAITALL is coalesced: Detcore neither loops for it beyond the would-block retry nor completes a successful short attempt, so a stream receive can return a short count where Linux would wait for the full count (G13); SO_RCVLOWAT is coalesced in the same way. TCP MSG_OOB should never block on Linux, but on a logically blocking socket the retry loop consumes its EAGAIN and waits. Every other flag — MSG_TRUNC, MSG_CTRUNC and the rest — is the kernel's alone on each attempt, and except on KVM Detcore synthesizes or clears no returned msg_flags bit.[c7][linux]

Interface fidelity. Except on KVM, the data, address, return count and error of the completing kernel attempt are the guest's, and the retry loop makes a blocking guest wait in scheduler order instead of host order; it does not deliver exactly what Linux would deliver, because a MSG_WAITALL stream receive can return a short count (G13).[c8][linux] The fidelity differences are Detcore's own and are stated rather than hidden. First, the guest-memory reads before the receive — with virtual time the header and control-region reads, and on sock-diag and route sockets under metadata virtualization the header and iovec-array reads — can answer EFAULT before any datagram is consumed; for the control region Linux would not fail at all, because it ignores a put_cmsg error and returns the data with a zero msg_controllen (G19).[c4] Second, where that snapshot shows a write the receive makes could land on the msg_namelen Linux re-reads afterwards, the call is refused before receiving: under the fail-closed policy the run ends, and only under --allow-unsupported-syscalls does the guest get EOPNOTSUPP without receiving, rather than risk delivering a host timestamp Detcore could not find to replace; this refusal precedes Linux's own errors. After a receive, the same inability in a permissive run warns and keeps the kernel's control bytes, host timestamp included, while a fail-closed run ends (see the refusal order).[c4][c5] Third, timestamps are the logical receive time observed after the completing attempt, not the kernel's packet-arrival time, by design of virtual time. Fourth, peer credentials and non-timestamp control data keep host values except on KVM, where the provider strips them (G3, G9). Fifth, a sock-diag reply's supported identities are canonicalized under metadata virtualization where Linux delivers the host's.[c23][linux]

Every refusal and error, in the order it is decided. Detcore has no deterministic classification refusal for this call (code facts in the Appendix): no fixed errno answers it under the fail-closed policy merely for being recvmsg, and the geometry refusals below are conditional, not a classification refusal.[c18][c17] Its own decisions, in order, are these. Before typed dispatch (after the LiteInst phase-one gate in dispatch order), under network record/replay (--record-networking or --replay-networking) the network trace claims every recvmsg before typed dispatch: on a recorded TCP channel the run ends by name — "network trace does not model recvmsg on a recorded socket" — whatever the policy, and outside a channel the run ends after the receive if a descriptor delivered over SCM_RIGHTS is a non-AF_UNIX socket, if such a descriptor cannot be classified, or if the delivered control bytes cannot be read (G14). On in-guest LiteInst, first in dispatch order, where the process's SIGALRM disposition is a guest handler, signal phase one answers every recvmsg with EOPNOTSUPP before typed dispatch, and the policy does not change that answer (G10). Second, the guest-memory reads before the receive: with virtual time the header read (for every call that names a header) and the control-region read, and on sock-diag and route sockets under metadata virtualization the header and iovec-array reads whatever the time setting — a guest-memory failure there (EFAULT) precedes any descriptor decision, where the kernel answers EBADF for a bad descriptor before it copies the header, so for a bad descriptor with an unreadable header or control buffer Detcore's EFAULT precedes the kernel's EBADF (G11) and likewise precedes Linux's first check, MSG_CMSG_COMPAT EINVAL (G12); the entry geometry itself answers no EFAULT. On KVM the provider instead answers EBADF for an unknown guest number first, then probes the header, name and control buffers with EFAULT, and refuses oversized payload, name or control with EINVAL (G9).[c3][c4][linux] Third, the pre-receive geometry refusal, before anything is received, where the control layout cannot be trusted to let Detcore find the timestamps it may have to replace: under the fail-closed policy the run ends, and only under --allow-unsupported-syscalls does the guest get EOPNOTSUPP without receiving; it precedes Linux's EINVAL, EBADF and not-a-socket errors.[c4] Fourth, a descriptor Detcore cannot classify decides nothing: the call runs on the blocking path and the kernel's own EBADF, not-a-socket error, header-copy EFAULT and MSG_CMSG_COMPAT EINVAL decide it in the kernel's order — noting that Linux gives the EINVAL before its descriptor check, while Detcore's pre-reads above can precede both (G12).[c6][linux] Fifth, on a classified descriptor each kernel attempt takes the kernel's own order — descriptor, socket, copy and protocol errors, including EINVAL for an unusable message — except that a would-block result on a logically blocking call is consumed by the retry loop and reaches the guest only as the timeout's EAGAIN, a signal's interrupt errno, or the read-shutdown zero described above, never as a bare EAGAIN from an intermediate attempt.[c7][c8][c19][c20] Sixth, after a successful receive, an untrusted SCM_RIGHTS layout that may have installed descriptors ends a fail-closed run as a policy refusal (the receive has already run, so no permissive errno replaces its result), and the post-receive timestamp refusal does the same; in a permissive run both warn and keep the kernel's result and control bytes.[c11][c5] On KVM the provider's own errno refusals and run ends replace this order (G9). The precedence differences from the kernel are the pre-dispatch, first, second, third and sixth decisions: the kernel has none of them in those positions.

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c2] What the subscription records depends on the descriptor, not on the flag: an internal descriptor (a pipe or socketpair endpoint, or under record/replay a socket whose peer is a guest) polls through the record/replay subtool, so every attempt — each EAGAIN and the completing receive with its data, address and control bytes — is a recorded event replay reproduces, and replay therefore re-delivers the same message, the same installed numbers as stand-ins rebuilt from the recorded descriptor facts, and the same joined open files where the recording joined one.[c19][c21] An external descriptor under record/replay runs on the blocking path through record/replay, which records the kernel's answer to the one blocking call; replay returns that answer without receiving again. In a plain run there is no recorder: internal attempts execute directly and no attempt is recorded, while the descriptor recording after a successful receive still runs from live kernel facts exactly as under record.[c19][c11] The timestamp rewrite needs no recording of its own in either mode: the logical receive time is re-derived in replay from the same schedule, and the rewrite is applied to the reproduced control bytes as it was to the recorded ones.[c5] Under network record/replay the trace takes the call over before this subscription applies, and ends runs as stated in the refusal order (G14). Under record and replay the read-shutdown finish never runs, so a blocking datagram receive on an internal socket after the guest's own SHUT_RD waits forever where Linux returns zero (G15). Replay writes back the whole msghdr, whereas Linux writes only the name length, the flags and the control length, and replay asserts that the guest's buffers match the recording.

Known gaps

  • G1 (by design; DBT copied child only): in a DBT copied child — the window between a vfork and the exec of the child's next program, where no Detcore tool runs — this call never runs natively, under any policy: every recvmsg, including one without a control buffer, is refused there, because that ABI cannot read the guest's msghdr to tell whether an SCM_RIGHTS message would import an open file description another process's Detcore state holds a claim about. Under the default fail-closed policy the run ends by name; under the explicit allow-unsupported opt-out the call answers EPERM without executing. The copied-child policy in inguest-engine/src/native/copied_action.rs:163-182 (named here as text evidence, not as a checked citation) names recvmsg/recvmmsg together and tests both policies, so this gap cites the dispatch it bypasses and the refusal-set exclusion it complements.[c2][c18] On the ptrace backend (including e9patch preprocessing, which is not a backend), KVM and SaBRe the same call reaches the handler above, and on LiteInst it reaches the handler except under a guest SIGALRM handler, where phase one refuses it first (G10); a guest that must receive in the copied-child window must avoid that window — there is no fallback inside the call on DBT.
  • G2 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): an external socket's message is still the host's: what a host peer sends, when it sends it, and whether an external descriptor's blocking call completes are whatever the host does when the forwarded call runs, so a peer or network that changes under the run, or differs between hosts, changes what the receive delivers, and Hermit makes this call repeatable only so far as that peer repeats, because every backend except KVM forwards through the same handler, and on KVM the provider forwards to the host in its place (G9).[c6][linux]
  • G3 (unimplemented; ptrace including e9patch preprocessing, DBT outside a copied child, SaBRe, LiteInst): SCM_CREDENTIALS and all non-timestamp, non-SCM_RIGHTS control data pass through with host values: a credential message names the host sender's pid/uid/gid, which need not repeat across hosts or runs, and no control type other than the timestamp kinds is parsed for canonicalization. KVM is excluded here because its provider strips this data instead (G9).[c11][c12] A guest that must not observe host credentials must not request them; there is no rewriting inside the call.
  • G4 (unimplemented; ptrace including e9patch preprocessing, KVM, LiteInst): a receive that completes on the background path — physically blocking, unclassifiable, non-sequentialized, or external under record/replay — has its delivered descriptors never recorded, because another task may have closed or replaced their numbers, or rewritten the control data, before the caller resumes; a later call through an unrecorded number runs outside Detcore's table model for it, and without sequentialized threads no receive is recorded at all. On SaBRe and DBT, which discover descriptors instead of recording them, this gap does not apply: the first later call that names the number discovers it.[c6][c11] A guest that passes descriptors must receive them in-turn; there is no retroactive recording inside the call.
  • G5 (unimplemented; ptrace including e9patch preprocessing, KVM, LiteInst): even in-turn, a received anonymous inode other than an inotify instance (eventfd, signalfd, timerfd, epoll, pidfd, userfaultfd and kin that did not join a sender-modeled file), a number that already has a record, and a descriptor whose facts cannot be taken are left unrecorded with a warning, so later calls through them take paths that may be wrong for their kind. On SaBRe and DBT this warning list does not apply: a receive there records nothing and the number is discovered later, where a received inotify instance has its F_GETFL, and any read that finds nothing queued, refused by name.[c11][c21] A guest receiving such descriptors gets the kernel's data and numbers but not Detcore's model of them; there is no fallback inside the call.
  • G6 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the timestamp rewrite runs only where time is virtualized and the message names a control buffer; otherwise a SCM_TIMESTAMP* value the kernel writes is the host wall clock at packet arrival, unrepeatable by construction.[c4] A guest that must not observe host time must run with virtual time; the call itself does not refuse host timestamps outside it, except in the DBT copied child (G1).
  • G7 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT, SaBRe, LiteInst): guest programs recvmsg_scm_rights_mmap, datagram_read_shutdown, binder_fd_passing, record_replay_scm_rights and scm_rights_received_descriptors under tests/c exercise an SCM_RIGHTS receive over an mmap'd control buffer, a datagram receive after read shutdown, descriptor passing through binder, recorded descriptor passing, and received-descriptor classification as text, unit coverage pins the timestamp rewrite to the written control bytes, MSG_DONTWAIT's run-once fate and MSG_ERRQUEUE marking, the guest program at tests/c/socket_timeout.c:190 (named here as text evidence) runs recvmsg with SO_RCVTIMEO on an empty socketpair, which is the SO_RCVTIMEO EAGAIN case, and no machine-verified coverage at the pin distinguishes the MSG_WAITALL short-attempt fate, the timed-wait EINTR, credential pass-through, or the in-turn versus background recording split across the ptrace backend (including e9patch preprocessing), KVM, DBT, SaBRe and LiteInst; each is therefore claimed from the handler code above, not from a measured run.[c7][c11]
  • G8 (unmeasured; ptrace record and replay, KVM record and replay): under replay an external receive returns the recorded kernel answer without receiving, and an internal one reproduces every recorded attempt, but whether a replayed run's later calls through descriptors the recorded receive installed observe the same open files — where the live host state behind a stand-in has since changed — is claimed from the record/replay descriptor rebuild, not measured at the pin; the recorded numbers and joins are repeated, the host descriptions behind unjoined stand-ins may not exist.[c19][c21]
  • G9 (unimplemented; KVM): on KVM the reverie-linuxemu provider in executor/socket.rs (named here as text evidence, not as a checked citation) answers every recvmsg instead of the kernel: it keeps only SCM_RIGHTS and the six timestamp types and strips everything else including SCM_CREDENTIALS and SCM_PIDFD (closing the pidfd), sets MSG_CTRUNC even when the guest's buffer had room, installs rights at the lowest free numbers of its own guest table, runs every host receive with MSG_DONTWAIT | MSG_CMSG_CLOEXEC while clearing MSG_CMSG_CLOEXEC from the returned msg_flags when the guest did not ask for it, answers EBADF for an unknown guest number before Linux's MSG_CMSG_COMPAT EINVAL, probes the header, name and control buffers with EFAULT (a null control buffer with nonzero length included, where Linux succeeds), refuses oversized payload, name or control with EINVAL where Linux clamps or does not limit, refuses with ENOMEM when fewer than SCM_MAX_FD descriptors are free, with ENOSYS for a record socket whose buffer is not all writable while a tracked right is in flight, and with EACCES for a received real procfs right after the host consumed the message, and ends the run — with no errno to the guest — for lost rights, a late receive fault, or an unseen right discard. A guest on KVM must not rely on kernel ancillary, flag, error-order or refusal behaviour for this call; there is no kernel fallback inside the call.[c2]
  • G10 (unimplemented; LiteInst in-guest): where the process's SIGALRM disposition is a guest handler, which only in-guest LiteInst publishes, signal phase one answers every recvmsg with EOPNOTSUPP before typed dispatch, because the call is in none of the phase-one allowed sets, and the fail-closed policy does not change that errno. A guest that installs a SIGALRM handler on LiteInst cannot receive with this call in that state; there is no fallback inside the call.[c24]
  • G11 (unimplemented; ptrace including e9patch preprocessing, KVM, where Detcore's reads precede the provider's, DBT outside a copied child, SaBRe, LiteInst): with virtual time Detcore reads the message header and the control region before the kernel sees the call, so a guest-memory EFAULT from those reads precedes Linux's EBADF and not-a-socket errors for a bad descriptor with an unreadable header or control buffer, where Linux answers the descriptor error first. A guest with both faults gets EFAULT, not the kernel's descriptor errno; there is no reordering inside the call.[c4]
  • G12 (unimplemented; ptrace including e9patch preprocessing, KVM, where Detcore's reads precede the provider's, DBT outside a copied child, SaBRe, LiteInst): the same pre-receive header and control-region reads precede Linux's first check, MSG_CMSG_COMPAT EINVAL, so a guest with an unreadable header or control buffer and the compat flag gets EFAULT where Linux answers EINVAL first; Detcore's sibling recvmmsg entry check documents that same compat-flag refusal.[c28] There is no reordering inside the call.[c4]
  • G13 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): MSG_WAITALL and SO_RCVLOWAT short counts on stream sockets are returned unchanged: because Detcore keeps the socket physically nonblocking, a stream receive returns what it has copied instead of waiting for the full count as Linux would, and nothing completes the count. This flag is coalesced, not faithfully implemented. A guest that needs the full count must loop itself; there is no completion inside the call.[c7]
  • G14 (unimplemented; network record/replay on ptrace including e9patch preprocessing, KVM, DBT, SaBRe, LiteInst): under --record-networking or --replay-networking the network trace claims every recvmsg before typed dispatch: on a recorded TCP channel the run ends by name whatever the policy, and outside a channel the run ends after the receive when a descriptor delivered over SCM_RIGHTS is a non-AF_UNIX socket, when such a descriptor cannot be classified, or when the delivered control bytes cannot be read. A guest in this mode cannot receive on a recorded TCP channel with this call; there is no fallback inside the call.[c25]
  • G15 (unimplemented; record and replay): under record and replay the read-shutdown finish is skipped, so a blocking datagram receive on an internal socket after the guest's own SHUT_RD never finishes where Linux returns zero, and a thread that shut the socket down and joined the reader waits forever. A guest under record and replay must not rely on read shutdown ending this call; there is no finish inside the call in that mode.[c20]
  • G16 (unimplemented; ptrace including e9patch preprocessing, LiteInst): a pidfd installed by SCM_PIDFD is never recorded: Detcore reads only SCM_RIGHTS from received control data, so the pidfd sits in the guest's table but not in Detcore's, later calls through it fail with EBADF, and replay reserves stand-ins only for SCM_RIGHTS numbers. SaBRe and DBT discover the pidfd instead and record it as an ordinary regular file, so there the descriptor is modelled as the wrong kind rather than refused. On KVM the provider closes the pidfd instead (G9). A guest must not use a received pidfd through Detcore; there is no recording inside the call.[c26]
  • G17 (unimplemented; ptrace including e9patch preprocessing, KVM, LiteInst, SaBRe and DBT on discovery): a received descriptor that joins no sender-modelled file is recorded with the host's status flags, Detcore's own O_NONBLOCK included, so a blocking read through it can return EAGAIN where Linux would wait. Only an inotify instance gets an unknown blocking mode. A guest must not rely on the received descriptor's blocking mode matching Linux; there is no correction inside the call.[c27]
  • G18 (unimplemented; LiteInst and in-guest-trap always, and the shared-tool backends wherever Detcore cannot match the file): a received per-process record file that joins no modelled file has every later read and seek refused by name. A guest receiving such a file gets the descriptor but not usable reads through it; there is no fallback inside the call.[c27]
  • G19 (unimplemented; ptrace including e9patch preprocessing, KVM, where Detcore's reads precede the provider's, DBT outside a copied child, SaBRe, LiteInst): an unreadable control region answers EFAULT and consumes nothing, where Linux ignores the put_cmsg error, returns the data with a zero msg_controllen, releases the rights and sets MSG_CTRUNC. A guest with an unreadable control buffer loses a receive Linux would complete; there is no tolerant path inside the call.[c4]
