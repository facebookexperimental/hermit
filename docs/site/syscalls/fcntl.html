fcntl (72)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-21 at 403e350e9e82

In short

Natively, fcntl is a switchboard over one descriptor: it duplicates it, reads and writes its descriptor and status flags, takes, queries and releases POSIX and open-file-description (OFD) byte-range locks, grants leases, names the process Linux signals when data arrives, sizes pipes and seals memory files — and the waiting forms sleep in the kernel until another process lets them proceed. Outside a DBT copied child, Hermit determinizes the switchboard as a whole while modelling only a few positions itself: descriptor duplication and the close-on-exec and status-flag writes update Detcore's own descriptor model around a forwarded call, the status-flag read rewrites the physical flag word into the guest's logical one, pipe growth past a pinned ceiling is refused and a pipe-size read is clamped to that ceiling, lock, lease, owner, seal and hint commands are forwarded under record and replay with only bookkeeping afterwards, the blocking lock waits are forwarded as written in the caller's turn with no scheduler admission and no nonblocking probe — the exact point where this call can wedge a sequentialized run — and two forwarded reads end the run instead of answering: a status-flag read whose blocking mode Detcore cannot tell, under the fail-closed policy, and a pipe-size read on a host whose pipe ceiling is below two pages, with no policy condition. On KVM the forwarded call is answered by the provider named below rather than by the host kernel, in a LiteInst in-guest process that handles the virtual alarm signal every fcntl is refused before dispatch, and inside a DBT copied child only an OFD lock change is refused while every other command runs natively. Known gaps: 18.

Determinism strategy

What is nondeterministic natively. The entry first takes the descriptor: a descriptor the caller does not hold is EBADF, and an O_PATH descriptor admits only the duplication commands, the two descriptor queries (F_DUPFD_QUERY and F_CREATED_QUERY), the descriptor-flag commands and the status-flag read, and refuses the rest with EBADF, before the command switch runs at all.[linux] Inside the switch each command draws on different host state: duplication on the caller's descriptor table, the status flags on the open file, a lock command on every other process's locks on that file — a waiting form sleeping interruptibly until the conflicting lock goes, with POSIX deadlock detection returning EDEADLK for a waiting cycle and no such detection for OFD locks, whose detector entry returns at once — a lease on later opens of the file, an owner command on which process exists to be signalled, a pipe size on the host's pipe ceiling, and a seal on the memory file's own state.[linux] The return value, any flock structure written back, whether the call waits at all, and what later calls observe can therefore all move with host state and host timing.

What Hermit does. Outside a DBT copied child, Detcore determinizes fcntl by keeping one shared typed dispatch to one handler: classification places the entry with the determinized calls, and typed dispatch reaches the handler in files.rs, with the call always observed.[c1][c2] Three answers can still precede that dispatch. In a LiteInst in-guest process whose virtual-alarm disposition is a guest handler, every fcntl — the descriptor-flag and status-flag reads included — is refused with EOPNOTSUPP before typed dispatch, because the call is placed in none of the phase gate's admitted sets and the module names it among the refused calls (G11).[c29] A /proc directory Detcore serves on a placeholder, present where the tool does not share the guest's descriptor table and not under record and replay, is answered by the placeholder emulation before dispatch, and a rendered procfs file is answered before dispatch for the seal, lease, hint and status-flag cases named below (see the refusal order).[c30][c32] The handler then decides a small set of commands itself, screens the owner and signal commands before anything reaches the provider, forwards every remaining command — including every lock query, every seal and every read/write hint — unchanged under the record and replay wrapper, and does its bookkeeping after the forwarded call returns.[c3][c25] There is no per-command emulation of a lock, a lease or a seal inside the handler: on the ptrace family (every backend except KVM) the host kernel's lock manager, lease manager and memfd seals decide those calls, while on KVM the provider named in the backend paragraph decides them instead, and Detcore's part is the descriptor model it keeps beside the descriptor table, the /proc/locks ledger it refreshes after a lock change, and the refusals below.[c3][c9] Three screens run before the command switch, in this order, and a refused call has no other effect. First, an F_SETSIG naming a signal the run reserves for in-guest use is refused with EPERM by the reserved-signal policy, after an O_PATH descriptor is answered EBADF at the same descriptor read Linux's own O_PATH gate uses.[c3][c36] Second, only on the in-guest route that refuses host-timed producers, an operation that would complete such a producer — naming a nonzero owner, turning asynchronous delivery on, taking a read or write lease, or arming a directory notification with an event bit — is refused with EPERM where it would complete one, with Linux's earlier answers preserved inside that refusal: EBADF for a descriptor not held or an O_PATH one, ENOTDIR for a notification on a non-directory, and EINVAL for a lease on a non-regular file; where the kernel would instead give its lease ownership refusal for a caller that neither owns the file nor holds the lease capability, the screen still answers EPERM for a regular file, because a lease always completes a producer there.[c20][c22][linux] Third, an owner command naming one of Hermit's own tasks — F_SETOWN with a positive pid, or F_SETOWN_EX naming a thread or process owner — is refused with EPERM, and an F_SETOWN_EX owner is read once and reaches the provider as Detcore's scratch-stack copy, so another guest thread rewriting the argument between the check and the provider read cannot change the owner the provider sees; an unreadable owner fails with EFAULT at that read.[c21][c23] After the screens, an F_SETSIG of SIGKILL publishes a run-wide reserved-input exposure (it changes no guest-visible result of this call), the signals this command lets Linux send at a host-chosen moment are computed as a set, a set naming SIGALRM — and any non-release lease, separately — is refused where the virtual-SIGALRM policy refuses arming a producer, and where the backend's host-timed signals are physical those signals are recorded for the whole container before the call runs.[c3][c17] One delegation word escapes every screen: the delegation-setting lease word decodes as an unlisted word rather than as a lease, so it bypasses the producer screen, the non-release-lease alarm refusal and host-timed recording, and reaches the provider as a forwarded lease (G15).[c3][c17]

Interface fidelity. Honoured, modelled, rewritten, refused and forwarded behaviour differs per command, and the table is the checked coverage: *modelled* means Detcore updates its own model around the forwarded call, *rewritten* means the guest sees a value Detcore computed, *refused* means Detcore answers without the kernel deciding, and *forwarded* means the deciding provider's own result, output structure and error under the record and replay wrapper — except the two outputs G18 names, which replay does not write at all — issued whole so its partial-completion and restart behaviour is preserved rather than remodelled: on the ptrace family that provider is the host kernel, and on KVM it is the provider named in the backend paragraph, whose lock, lease, seal, hint and owner answers therefore differ as G10 states.[c3][c25][c9]

The sixty-four-bit lock words and the per-file hint words above have no Detcore case deciding their answer — the two setting lock words are matched only to refresh the lock ledger where it takes the backend's fact — so forwarded whole, they take the kernel switch's default answer on the sixty-four-bit fcntl entry, while only the compat and sixty-four-bit-named entries handle the lock words and only the per-descriptor hint words have a case, so a guest meets that default refusal rather than a lock or hint answer on any backend whose provider follows the kernel switch (G10 states where KVM differs).[linux][c25][c9] The delegation-setting word likewise has no Detcore case and is forwarded as an unlisted word, as the screens paragraph states.[c25] The status-flag pair is the one place the same descriptor has two flag words. Physically, Detcore keeps scheduler-managed descriptors nonblocking so its own polling and retry discipline works; logically, the guest sees only what it set. F_SETFL therefore forwards the guest's flags with O_NONBLOCK added where the predicate holds — the run must be sequentializing threads without externally visible socket debugging, and then pipes and internal sockets already physically nonblocking in record/replay modes, and pipes, internal and ordinary sockets, event files and inotify instances outside them, never for an inherited descriptor with an external reader — records the guest's flags as the logical word, marks the description physically nonblocking, and publishes pipe status where that publication applies.[c5][c19][c24] F_GETFL reads the physical word through the wrapper and answers the logical one: O_NONBLOCK as the guest set it, with O_NOFOLLOW restored for a rendered procfs file whose placeholder was reopened without it.[c4][c18] The one exception is an inotify descriptor received without the open file description its sender modelled, whose physical O_NONBLOCK may be Detcore's own: under the fail-closed policy F_GETFL on it ends the run with the policy-refusal exit rather than answering at all — the guest never sees an errno from that call — and outside that policy the logical word is answered as recorded (G6).[c4][c33]

Pipe sizing is pinned to one value with three faces that the code keeps as one rule: the capacity a Detcore-created pipe is pinned to, the maximum /proc/sys/fs/pipe-max-size reports, and the ceiling a guest may raise a pipe to are all two host pages.[c15] A growth request above that ceiling is refused with EPERM — the errno Linux itself gives when its host ceiling binds — without consulting the host ceiling and before the kernel's own descriptor refusals for a closed, path-only or non-pipe descriptor and its watch-queue refusal, so the same guest gets the same answer on a default and a hardened host; a request at or below it, shrinking included, is forwarded.[c7][c16][linux] The request is a signed word, so a request with its high bit set is negative and is forwarded rather than refused, and a caller the host lets grow past the advertised ceiling still has its size read clamped to the ceiling.[c16][c7] Inside the forwarded band the host still decides: growth past the host ceiling and growth while the caller's host-wide pipe accounting stands over its soft or hard limit are refused by the host, so a guest that shrinks a pipe and grows it back toward the pin can meet a host-load-decided refusal even on a default host (G17).[c7][linux] A size read is forwarded and then reported no larger than the ceiling, so an inherited pipe the host sized by load reads the same in every run, while the pipe's real capacity — and how far a write to a host-drained pipe completes — is unchanged.[c7] Where the host's own pipe ceiling is below two pages, host load decides a new pipe's capacity and no pin can hold: a size read there ends the run with the policy-refusal exit rather than report a host-chosen capacity.[c7]

Lock bookkeeping. A lock itself is always the kernel's; what Detcore keeps is which locks each open file description holds, for its rendered /proc/locks. After an OFD lock or unlock — and, only where the ledger takes the backend's fact, after a POSIX lock, unlock or lease — the description's locks are re-read and the ledger updated: through the descriptor's fdinfo, read through an anchor proved to be procfs, where the tool can name guest descriptors that way, and from the backend's descriptor-status fact where it cannot and Detcore renders procfs.[c8][c9][c26][c27] Where the backend holds a guest record lock as an OFD lock of the description — on KVM every forwarded record lock, as G10 states — that lock belongs to the open file description rather than to the process, closing another descriptor of the file does not release it, a forked child shares it, and the kernel's POSIX deadlock detection does not run for it; it is shown on no /proc/locks row and no fdinfo line, its query reports no owning pid, and a snapshot that would show it is refused by name.[c9] A re-read that fails because the guest's filesystem view or the backend decides so leaves the description untracked and contributing no lock; one that fails for ambient or resource state leaves its locks unknown, and a later /proc/locks read refuses while a guest table references the description.[c26] None of this changes the guest's own lock call: the refresh runs after the forwarded call returns, and its failure modes govern later /proc reads, not this call's result.

Every refusal, in the order it is decided. Detcore has no deterministic refusal for this call as a whole (code facts in the Appendix): the syscall is not in the deterministic-refusal set, so outside the phase gate (G11) no mode answers the call itself with a fixed errno, and the copied-child gate below therefore lets every command except an OFD lock change through natively.[c10] Its own decisions, in order, are these. First, on LiteInst in-guest in a process that handles the virtual alarm signal: EOPNOTSUPP for every fcntl before typed dispatch (G11).[c29] Second, before dispatch on a descriptor Detcore itself serves: on a placeholder /proc directory a path-only placeholder answers EBADF to every command except the status-flag read, the two duplications, the descriptor-flag read and write and the two descriptor queries; on any other placeholder every record lock and lock query, POSIX and OFD, ends the run under the fail-closed policy and answers ENOLCK under the allow-unsupported opt-out, a directory notification returns success and no event is ever sent, leases, seals, pipe sizes, hints, the status-flag read and the two descriptor queries are emulated including the O_NOATIME owner refusal and the direct-I/O refusal, the two duplications, the descriptor-flag read and write and the seven owner and signal commands return no placeholder answer and reach the handler, and every other command is refused as invalid; on a rendered procfs file the seal, lease, hint, lease-query and status-flag cases are answered before dispatch, including the same owner and direct-I/O rules for a status-flag write (G12, G13).[c30][c31][c32] Third, for F_SETSIG of a reserved in-guest signal: EBADF for an O_PATH descriptor at the descriptor read, then the reserved-signal refusal with EPERM for that signal.[c3][c36][linux] Fourth, on the producer-refusing in-guest route only: EBADF, ENOTDIR or EINVAL for the pre-arming states above, then EPERM where the operation would complete a host-timed producer, including where the kernel would give its lease ownership refusal first on a regular file.[c20][c22][linux] Fifth, for owner commands: EFAULT for an unreadable F_SETOWN_EX owner at Detcore's single read, then EPERM for an owner naming one of Hermit's tasks; both come before the kernel's descriptor refusal for a closed or path-only descriptor on the same call, because the single read runs ahead of the forwarded call.[c21][c23] Sixth, EPERM from the virtual-SIGALRM policy where the command's host-timed set names SIGALRM, and separately for any non-release F_SETLEASE, because a lease break waits interruptibly with no scheduler admission.[c3] Seventh, inside the switch: the run-ending policy refusal for F_GETFL on a blocking-mode-unknown inotify descriptor under the fail-closed policy, with no errno reaching the guest; the run-ending policy refusal for F_GETPIPE_SZ on a host below the two-page pipe floor; and EPERM for F_SETPIPE_SZ above the pinned ceiling, ahead of the kernel's descriptor and watch-queue refusals.[c4][c7][c33][linux] Eighth, the descriptor-model lookup: only a status-flag write and the reserved-signal screen look the descriptor up before the forwarded call, so only they fail there on a descriptor Detcore does not track; the status-flag read, the descriptor-flag write and both duplications look up after the forwarded call, so the provider acts first and the guest then meets the model refusal — after a duplication the new descriptor stays open in the guest's table, unreported — while every other command and both OFD arms reach the provider, which decides the call, and the later refresh tolerates an unmodelled descriptor (G14).[c4][c5][c6][c34] Ninth, every forwarded command takes the deciding provider's own order through the wrapper: on the ptrace family EBADF for a descriptor not open or an O_PATH descriptor outside its admitted commands, EFAULT for a lock or owner structure the provider cannot copy, then the command's own errors — the default refusal for an unknown word, for the sixty-four-bit lock words and for the per-file hint words, and for a malformed lock (an OFD request naming a pid included), the provider's conflict and detected-cycle answers for a lock, EPERM for pipe growth past the host ceiling at or below Detcore's pin, and the file's own errors for a lease, seal or hint the file does not admit; on KVM the provider's own order in G10 replaces this one.[linux][c25] The precedence differences from the kernel are the screens and the pre-dispatch answers: Linux has no phase-gate, placeholder, rendered-file, reserved-signal, producer, Hermit-owner or SIGALRM-arming refusal in any position, its fault for an F_SETOWN_EX owner follows its descriptor checks where Detcore's single read precedes them, and its pipe refusal follows its host ceiling where Detcore's follows the pin.[c3][c21][linux]

Blocking lock waits and the scheduler. This is the claim the page must not soften. A waiting lock command — F_SETLKW and F_OFD_SETLKW, and a lease break's wait behind F_SETLEASE — is forwarded exactly as the guest wrote it on the ptrace family; the sixty-four-bit waiting word takes the default refusal above and never sleeps, and on KVM a forwarded record wait sleeps as an OFD wait in the provider, with no POSIX deadlock detection and no owning pid to report (G10), through the same in-turn record and replay wrapper as every other forwarded command: the handler does not rewrite it to its non-waiting form, does not probe, and does not ask the scheduler for a blocking-external-operation admission of the kind the genuinely blocking I/O handlers use.[c8][c9][c25] The guest thread therefore sleeps inside the kernel's interruptible lock wait — the wait Linux itself uses, which wakes when the conflicting lock is deleted or a signal interrupts it — while Detcore's sequentialized scheduler believes the thread is still in its turn.[linux] No other guest thread runs to release the conflicting lock, because releasing it is exactly the turn the scheduler cannot take. Where the conflicting lock is held by another guest thread of the same run, the run wedges: not a wrong answer but no answer, until a host-timed signal interrupts the wait or the run is killed from outside. The sibling flock handler exists in its present form precisely because this wedge was measured there — a contended four-way guest hung indefinitely under plain forwarding — and it answers by probing non-blockingly and refusing a contended blocking request — ending the run under the default fail-closed policy, with ENOLCK only under the allow-unsupported opt-out — restoring any lock the probe's non-atomic conversion dropped; fcntl has no equivalent probe, refusal or restore at this pin.[c28][c33] Deadlock splits by lock class, faithfully and badly. For a waiting POSIX lock on the ptrace family Linux detects a waiting cycle and answers with its deadlock error, so a true POSIX deadlock across guest threads fails instead of sleeping forever — but only once the kernel wait is reached, and a cycle the sequential scheduler never lets form (the second waiter never runs) presents as the wedge above, not as a deadlock answer; on KVM that detection never runs, because the provider holds the lock as an OFD lock (G10). For a waiting OFD lock Linux performs no deadlock detection at all — its detector returns at once for an OFD caller — so even natively an OFD deadlock sleeps until interrupted, and under Hermit the same sleep additionally starves the releaser's turn: there is no execution, native or determinized, in which a deadlocked F_OFD_SETLKW answers with a deadlock error.[linux] A non-waiting lock never sleeps and is unaffected: F_SETLK and F_OFD_SETLK are answered for a conflict by the kernel at once in the caller's turn.[linux] Signals are the only exit Linux gives the wait, so a waiting lock under Hermit completes early exactly when a signal the scheduler delivers interrupts it — the interrupted error with no lock taken, or a restart where the handler's disposition requires one — and the schedule of that signal, not any lock state, decides the outcome.

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c1] What the subscription records for this handler is the kernel's answer to each forwarded command, in the caller's turn: the return value and, for a lock query, the flock structure the kernel writes back — a replayed F_GETLK returns the recorded conflicting lock and pid in that structure, not a fresh query against the replay host's locks.[c25] Two forwarded commands write output the wrapper does not record: F_GETOWNER_UIDS writes the owner uid pair and F_GETDELEG writes the delegation structure; replay writes nothing for either (G18). The modelled bookkeeping around the forwarded call — the descriptor-model update after a duplication or flag write, the logical flag word after a status read or write, the clamped pipe size — is re-derived in replay from the same recorded answers in the same schedule order and carries no recording of its own; the lock-ledger refresh likewise re-reads through the recorder, so a recording holds the fdinfo sequence after each lock change and replay matches its rows against the recording's locks, taking no real lock.[c26] The recorded outputs are the lock queries, the extended owner query and the read/write hint query, whose structures and values replay writes back rather than re-querying (hermit-record-format/src/event.rs, hermit-replay/src/replayer.rs); the two duplications and the descriptor-flag write replay by re-executing the recorded call through the replayer's dup-family and replayed-side-effect handlers and checking the result against the recording, panicking on a mismatch (hermit-replay/src/replayer.rs); every remaining command replays by its recorded status alone, so a command whose only effect is that unrecorded output replays as its status with the guest's memory unchanged.[c25] A waiting lock is the sharp edge: in a plain run it sleeps in the kernel as above; under record it sleeps the same way while recording, so the wedge is a recording-time wedge first; under replay the recorded answer is returned without waiting, so a replay never re-wedges on a lock its recording already holds the answer for — and never re-tests whether that answer still holds on the replay host.[c8][c25]

There is no second Detcore implementation of this call behind any backend switch. The same dispatch, handler, screens and bookkeeping run as the one shared Detcore tool on the ptrace (including e9patch preprocessing, which is not a backend), KVM, DBT-instrumented-root, SaBRe and LiteInst-in-guest executions, and divergence enters only through named capability and configuration conditions: whether the tool can name guest descriptors through the kernel's procfs (everywhere except KVM, where the ledger instead takes the backend's descriptor-status fact), whether the in-guest route refuses host-timed producers (the LiteInst-in-guest route; DBT does not), whether the backend's host-timed signals are physical (ptrace including e9patch preprocessing), whether the fail-closed policy is in force (the F_GETFL unknown-mode run end), the virtual-SIGALRM configuration (pipe-status publication), whether the process handles the virtual alarm signal on LiteInst in-guest (every fcntl refused before dispatch, G11), whether the descriptor is one Detcore itself serves on a placeholder or as a rendered file (answered before dispatch, never under record and replay for placeholders), and whether threads are sequentialized — the condition that turns the forwarded waiting lock from a sleep into a wedge.[c2][c27][c29][c30] On KVM the forwarded call itself is answered not by the host kernel but by the provider in reverie-linuxemu (reverie-linuxemu/src/executor/file.rs, reached from reverie-linuxemu/src/executor/dispatch.rs), which converts record locks to OFD locks, answers every command it does not list as not implemented, and accepts owners only for a private pipe its creator configured, as G10 states; every by-design claim below that names the host kernel is therefore scoped to the ptrace family unless it names KVM separately.[c9] The DBT copied (vfork) child is the one execution that never enters that tool, scoped in G1. Any stronger sameness claim across configurations would need a run, not this code reading, and this page makes none.

Known gaps

  • G1 (unimplemented; DBT copied child only): in a DBT copied child — the window between a vfork and the exec of the child's next program, where no Detcore tool runs — every fcntl command runs natively except an OFD lock change: F_OFD_SETLK and F_OFD_SETLKW in any form, an unlock included, are refused there (the run ends under the default fail-closed policy; ENOLCK under the allow-unsupported opt-out) because a native OFD change would leave the /proc/locks ledger's record of that description stale, while F_OFD_GETLK and every POSIX lock command stay native, POSIX rows not being the ledger's to keep.[c1][c2][c10] A waiting POSIX lock, a pipe growth past the pin, an owner naming any process and a seal therefore all take the host's answer in that window, in strict and non-strict modes alike for the OFD refusal and natively otherwise — including a waiting POSIX acquisition that can strand the child behind a parent waiting for it, which the copied child's flock arm refuses for exactly that reason while this call's arm lets it run — and on the ptrace backend (including e9patch preprocessing, which is not a backend), KVM, SaBRe and LiteInst the same commands reach the handler above except where G11 owns the call first. A guest whose lock, pipe or owner state in that window must repeat must avoid the copied-child path; there is no fallback inside the call on DBT.
  • G2 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a waiting lock command is forwarded in the caller's turn with no scheduler admission, no nonblocking probe and no refusal, unlike flock: where the conflicting lock is held by another guest thread, the sequentialized scheduler cannot run the releaser and the run wedges until an interrupting signal or an outside kill (see the blocking lock-wait paragraph above).[c8][c25][c28] A guest must use the non-waiting forms and test EAGAIN itself; there is no waiting fallback inside the call on any tool-entering backend.
  • G3 (by design, faithfully forwarded; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): an OFD deadlock has no EDEADLK exit on any backend, because Linux itself detects no OFD deadlock — its detector returns at once for an OFD caller — so a cyclic F_OFD_SETLKW sleeps interruptibly exactly as natively, compounded under sequentialization by the preceding gap's starved releaser.[linux] A guest must order its OFD locks itself; neither Linux nor Detcore breaks the cycle.
  • G4 (by design; ptrace including e9patch preprocessing, DBT outside a copied child, SaBRe, LiteInst): the locks, leases and seals themselves are the host kernel's on the host file: a file changed by a writer outside the run, a lock taken by a host process, or a filesystem that refuses a lease or seal for its own reasons decides the forwarded call when it runs, so Hermit makes this call repeatable only so far as that file and that host repeat, because those backends forward through the same handler to that kernel; on KVM the provider decides instead, as G10 states.[c25][linux]
  • G5 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): the pinned pipe ceiling is two host pages, derived once from the host's page size, so the pinned capacity, the advertised maximum and the growth ceiling are two host pages on any host: the same guest is refused the same growth on any host of one page size and a different growth on a host of another page size, while the advertised maximum itself reports that ceiling and the host page size is separately guest-visible, so a guest can learn the pin only by reading them, not from the refusal.[c15] A guest that must name its capacity must stay at or below the smaller pin; there is no fixed byte ceiling inside the call.
  • G6 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): outside the fail-closed policy, F_GETFL on an inotify descriptor received without its sender's modelled open file description answers the recorded logical word although the physical O_NONBLOCK may be Detcore's own, so the answered mode can be the opposite of the description's real mode; a fail-closed run does not answer it at all and ends with the policy-refusal exit, as the status-flag paragraph states.[c4][c33] A guest in a non-fail-closed run must not trust that one answer; there is no corrected answer inside the call.
  • G7 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT, SaBRe, LiteInst): guests at the pin do exercise non-waiting OFD and record locks, a lease and seals as text — the proc_locks and proc_fdinfo_lines guests under tests/c, the flock_shared_exclusive guest, the rendered_procfs_files guest, and the proc_locks_determinism test under hermit-cli/tests — but no guest at the pin exercises a waiting fcntl lock against a conflicting guest-held lock or a lease break end to end, so the waiting behaviour and the lease-break path are claimed from the handler and kernel code above, not from a measured run on any backend.[c8][c9]
  • G8 (unmeasured; ptrace record and replay): under replay every forwarded answer is the recording's, so whether a replayed lock query's recorded conflicting pid, a replayed waiting lock's recorded success, or a later /proc/locks snapshot observes the file the replay host now holds is claimed from the record and replay path, not measured at the pin; the recording side's answer is repeated, the host lock it names may not exist.[c25][c26]
  • G9 (by design; ptrace including e9patch preprocessing, DBT outside a copied child, SaBRe, LiteInst): seals and read/write hints are forwarded with no Detcore model at all, traced as unhandled with every other unlisted command word: a memfd's seal state and a file's hint are whatever the host file holds when the forwarded call runs, and an unknown command word receives the host kernel's answer for that word on that file, including its default refusal where the kernel gives one; on KVM every unlisted word receives the provider's ENOSYS answer instead, as G10 states.[c25][linux] A guest that must repeat a seal or hint outcome must repeat the file it applies to; the call adds no determinism there.
  • G10 (unimplemented; KVM): on KVM the forwarded call is answered by the provider in reverie-linuxemu (reverie-linuxemu/src/executor/file.rs, reached from reverie-linuxemu/src/executor/dispatch.rs; the pipe-owner model in reverie-linuxemu/src/executor/pipe_owner.rs), not by the host kernel: a record lock is taken as an OFD lock of the open file description with no owning pid, so it survives closing another descriptor of the file, is shared by a forked child, takes no part in POSIX deadlock detection, and its query reports no owner; every command the provider does not list — F_SETLEASE, F_GETLEASE, F_NOTIFY, F_ADD_SEALS, F_GET_SEALS, F_GET_RW_HINT, F_SET_RW_HINT, F_GET_FILE_RW_HINT, F_SET_FILE_RW_HINT, F_GETOWNER_UIDS, F_DUPFD_QUERY, F_CREATED_QUERY, F_SETDELEG, F_GETDELEG, F_GETLK64, F_SETLK64 and F_SETLKW64 among them — is answered with ENOSYS, where Linux answers these commands and never with ENOSYS, only the sixty-four-bit lock words and the per-file hint words taking its default EINVAL; and an owner or asynchronous-signal configuration is accepted only for a private pipe its creator configured with no owner or itself, every other descriptor, owner and process-group case taking the same ENOSYS answer.[c9][c25] A guest on KVM must use OFD locks where it needs record-lock behaviour, must not rely on lease, seal, hint, notification or delegation words, and has no host-kernel form inside the call there.
  • G11 (unimplemented; LiteInst in-guest): on LiteInst in-guest alone, in a process whose virtual-alarm disposition is a guest handler, every fcntl gets EOPNOTSUPP from the phase gate before the handler above, the descriptor-flag and status-flag reads included, where Linux would answer or refuse with its own result, so a guest in that process has no fcntl through this handler; there is no admitted form inside the call.[c29]
  • G12 (unimplemented; ptrace including e9patch preprocessing, KVM, LiteInst where Detcore serves placeholders): a record lock or lock query, POSIX or OFD, through a /proc directory Detcore serves on a placeholder not opened with O_PATH is refused before dispatch — the run ends under the default fail-closed policy and the opt-out answers ENOLCK — where the kernel would take or refuse the lock, so a guest in that case has no lock through this call on that directory; placeholders are served only where the tool does not share the guest's descriptor table and not under record and replay.[c30][c31][c33]
  • G13 (unimplemented; ptrace including e9patch preprocessing, KVM, LiteInst where Detcore serves placeholders): a directory notification through a placeholder /proc directory not opened with O_PATH returns success and no event is ever sent, where Linux arms the notification, so a guest waiting for that event waits for an answer this call never gives; there is no notifying form inside the call on that directory.[c31]
  • G14 (unimplemented; ptrace including e9patch preprocessing, KVM, LiteInst; SaBRe and DBT discover the descriptor): a descriptor Detcore does not track fails from its descriptor-model lookup — before the forwarded call for a status-flag write and the reserved-signal screen, and after the provider has acted for the status-flag read, the descriptor-flag write and both duplications, a duplicated descriptor staying open unreported — where Linux would answer through a descriptor it holds, and the refresh after every other command tolerates the unmodelled descriptor instead; SaBRe and DBT discover such a descriptor and answer through it, and there is no tracked form inside the call on the other backends.[c34][linux]
  • G15 (unimplemented; ptrace including e9patch preprocessing, DBT outside a copied child, SaBRe, LiteInst): the delegation-setting lease word F_SETDELEG is decoded as an unlisted word (reverie-syscalls/src/args/fcntl.rs), so it takes a delegation through the lease machinery with the caller as owner and a break signal to that owner, while bypassing the producer screen, the non-release-lease alarm refusal and host-timed recording that the lease-setting word takes — the screened lease word taking the producer screen's EPERM on a regular file in place of the kernel's lease ownership refusal EACCES — and other openers wait for its break with no scheduler admission; on KVM the word takes the ENOSYS answer in G10 and no delegation is taken; a guest that must not arm such a wait has no screened form inside the call.[c3][c17][linux]
  • G16 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): after a waiting OFD or record lock returns, the ledger refresh re-reads through the descriptor number the guest passed, so a sibling that closed or replaced that number during the wait makes the refresh read another file's locks or find none and hide every lock, where the sibling flock handler first re-resolves the open file description the call took and refreshes only through a slot still naming it; a guest in that race has no description-faithful refresh inside this call.[c8][c9][c35]
  • G17 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a pipe growth at or below the pin is forwarded, so the host's ceiling and its host-wide pipe accounting decide it: growth past the host ceiling, and growth while the caller's accounted pipe pages stand over the soft or hard limit, are refused by the host with EPERM, a watch-queue pipe is refused with EBUSY, and a guest that shrinks a pipe and grows it back toward the pin therefore meets a host-load-decided answer even on a default host; a guest that must repeat that growth must stay below every host limit it can meet, and there is no host-independent form inside the forwarded band.[c7][linux]
  • G18 (unimplemented; ptrace record and replay): replay does not restore what F_GETOWNER_UIDS and F_GETDELEG write back through the argument: the recorder keeps argument output only for the lock-query, extended-owner and read/write-hint words, so under replay the guest's uid pair or delegation structure keeps whatever its memory held while the recorded run saw the kernel's values, and a replay can diverge from its recording; on a host without checkpoint-restore the first answers EINVAL and only the delegation output is lost.[c25]
