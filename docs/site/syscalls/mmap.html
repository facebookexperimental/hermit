mmap (9)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-20 at 403e350e9e82

In short

Natively, mmap asks the kernel to place a mapping at an address the kernel selects or the guest fixes, backed by a file at an offset or by no file, under the requested protections, so the returned address, the bytes the mapping shows, and the faults it later takes all come from the host address space and the host file. Outside a DBT copied child, which runs it natively, Hermit forwards the guest's own call to the host kernel on the ptrace family and to the backend's own Linux provider on KVM and keeps only a model of what the mapping shares: before the call it resolves a shared file mapping to the file or open description behind the descriptor, and after a successful call it records that identity — or that the identity could not be resolved — so a later futex or store through another address can be told whether the pages are shared. The sibling calls munmap and mremap share the mapping-model maintenance and keep their own pages; they are cross-linked here and are not checked on this page. Known gaps: 14.

Determinism strategy

What is nondeterministic natively. mmap takes a descriptor's file where the call is not anonymous, checks length, offset and mapping type, selects or verifies the address, and installs the mapping with the requested protections.[linux] Where the guest gives no fixed address the kernel chooses the placement from the current layout of the address space, so the returned pointer shows that layout; a file-backed mapping then shows the file's pages, and a touch past the file's end faults with SIGBUS from the fault path rather than at the call.[linux] A MAP_FIXED call replaces whatever the range held, and a MAP_FIXED_NOREPLACE call fails where the range is occupied.[linux]

What Hermit does. Outside a DBT copied child, Detcore determinizes mmap by handling it with the shared typed handler: classification places the entry with the determinized calls, and typed dispatch reaches the handler.[c1][c2] The handler adds no address, protection or flag policy of its own on the ptrace family: the guest's call — address hint or fixed address, length, protections, flags, descriptor and offset — goes to the host kernel through the record/replay path unchanged, and the address the guest sees is the host kernel's answer; on KVM the same call goes instead to the backend's Linux provider, whose own placement, copied file bytes and descriptor reading are a gap below (reverie-linuxemu/src/executor/mm.rs, reverie-linuxemu/src/executor/dispatch.rs, reverie-kvm/src/runtime.rs).[c5][linux] The ptrace family is every backend except KVM (ptrace including e9patch preprocessing, DBT, SaBRe and LiteInst). The anonymous descriptor is descriptor -1; the zero device is /dev/zero. What Detcore does itself is bookkeeping around that call, in this order. First, for a shared call it resolves the backing before any page is mapped: a shared call through the anonymous descriptor needs no lookup; any other shared call records the offset, refusing a negative one itself (see the refusal order below), then names the object behind the descriptor — the file's device and inode where the descriptor's record carries them, otherwise the open file description's own identity — and a descriptor Detcore cannot look up at all is recorded as unresolved rather than refused.[c3] The model calls a shared mapping anonymous only for that descriptor, not for the anonymous flag, so a shared anonymous call naming any other descriptor is filed under that descriptor's object or left unresolved, and a shared mapping of the zero device through one descriptor reuses one object at offset zero, each as gaps below.[c3][c7] Second, a non-anonymous call through a descriptor, where the run holds a snapshot of the system property area, checks whether the descriptor maps a live property file Hermit did not redirect, and refuses that mapping as below.[c4][c12] Third, the call itself runs through record/replay, which in a plain run is the single injection of the same call on the ptrace family and the provider call on KVM.[c16][c5] Only after it succeeds does the model change: the new range first removes whatever shared record the range overlapped — so a fixed mapping over a shared one, private or shared, retires the old sharing record for the replaced part — and then a shared mapping is entered under the identity resolved before the call, an anonymous shared mapping under a fresh per-address-space sequence number, while a private mapping is entered nowhere: outside the overlap removal, the model tracks shared mappings only.[c5][c8][c20][c11] A successful non-anonymous mapping through a descriptor is also noted against its open file description, so the description — and a flock lock it holds — is kept after its last descriptor goes; the result is unchanged.[c6][c15] That model is what the rest of Detcore consults: a futex word inside a tracked shared mapping takes a shared key from the mapping's object and offset within it, and a word outside every tracked mapping takes a private key, while a store range is treated as possibly seen through another address whenever it overlaps a tracked mapping or any shared mapping was ever left unresolved.[c7][c9]

Interface fidelity. On the ptrace family the address, and every success the host kernel's placement gives, is the host kernel's for every call Detcore forwards, because the call is injected unchanged and its result returned unchanged: a hint is honored or moved by the host kernel's own unmapped-area search, the fixed forms replace or refuse as the host kernel decides, protections, grow and lock flags, huge-page and population flags all take the host kernel's own reading, and no flag is honored, coalesced or rejected by Detcore before the host kernel sees it; on KVM the provider gives each of those answers itself, as the gap below states (reverie-linuxemu/src/executor/mm.rs).[c5][linux] File-backed versus anonymous makes no difference to the forwarded call on the ptrace family: a private file mapping's copy-on-write, a shared file mapping's common pages, an anonymous mapping's zero pages, and a fault past the file's end are the host kernel's and the file's, exactly as the injected call and the later fault deliver them; on KVM the provider copies the file bytes and leaves past-the-end bytes zero with no such fault (reverie-linuxemu/src/executor/mm.rs).[c5][linux] The model's own length is the requested length rounded up to whole base pages, so a sharing query at a byte inside the last partial page is answered for the base page, which can differ from the host kernel's huge-page rounding for huge mappings.[c20][c21] Before the executor, Detcore stats and resolves the descriptor for the property check and reads a shared file mapping's offset, and the identity it keeps can miss an alias the kernel would give, as the gaps below state.[c3][c7] Detcore sees every shared mapping the guest makes through this call outside a DBT copied child, and its munmap and mremap siblings keep the model in step (their pages)[c10]; the other routes to shared memory do not bypass it silently — shmat and remap_file_pages are refused with a fixed ENOSYS in classification.[c9][c19]

Every refusal, in the order it is decided. First, in the networking trace modes (--record-networking and --replay-networking), an mmap through a recorded channel socket ends the run with the policy-refusal exit before Detcore's handler runs, because the trace path owns every call naming such a descriptor except the descriptor and path calls on its ordinary path, and mmap is not one of them.[c22] Second, for a shared call through any descriptor other than the anonymous descriptor, an offset that does not fit in an unsigned word is refused by Detcore itself with EINVAL, before the descriptor is looked up and before the executor runs: a negative offset therefore gets Detcore's EINVAL where the kernel would refuse a missing descriptor, refuse a regular file for its size, map a shared anonymous call that ignores the descriptor and offset, or map a character device, each as the gap below states with its kernel answer named there.[c3][linux] Third, where the run holds a property-area snapshot, a non-anonymous call through a descriptor that names a live property file Hermit did not redirect — or a descriptor whose check against the snapshot itself fails for any reason but a missing descriptor — is refused before the executor runs: under --allow-unsupported-syscalls the call gets EOPNOTSUPP on every backend; otherwise a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit, ends on DBT through its runtime exit path, and on SaBRe ends only the refusing process so the run can wait on stranded; the refusal is reported under the openat name, not this call's. A descriptor that is simply not there does not take this refusal and keeps the executor's EBADF below.[c12][c13][c14] Fourth, every forwarded call then takes its executor's own order without Detcore reordering it — the host kernel's own order on the ptrace family, whose unaligned-offset refusal comes before any descriptor lookup and whose bad-type refusal comes after placement and the no-replace check, and the provider's own copy of that order on KVM (reverie-linuxemu/src/executor/mm.rs).[linux] The precedence differences from the kernel are the first, second and third refusals: the kernel has none of them, so where they apply they precede each kernel answer they displace for an open descriptor and not only the missing-descriptor answer — the first is a mode-level takeover in the networking trace modes, the second by construction only where the offset is negative and the descriptor is not the anonymous descriptor, and the third by construction never for the missing descriptor itself.[c3][c12][linux] A failed call, from any of these, changes no model entry: the sharing record is written only after a successful result.[c5]

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c2] In a plain run the record/replay path is the single injection above, and the sharing model needs no recording because it is re-derived from the same sequence of successful calls.[c16][c5] Under record and replay the subscription serves the record/replay tool's own handler for this call, which treats anonymous and file-backed mappings differently (hermit-record/src/recorder/mmap.rs and hermit-replay/src/replayer/mmap.rs): an anonymous mapping is let through in both, on the stated premise that address-space randomization is disabled, while a file-backed mapping is recorded with its address and bytes and replay puts a mapping back at the recorded address without replacing an occupied one except for fixed-address calls, which replace as they did while recording, and a shared file mapping additionally carries the recorded file identity so replay can back every mapping of one file with one shared backing.[c16] Replay therefore does not ask the live host file or the live layout for the address or the bytes of a file-backed mapping: it repeats the recorded address, and a placement that cannot be put there is a replay refusal, not a moved mapping. What the subscription records for this handler, on the Detcore side, is nothing of its own: Detcore forwards the call to that tool and maintains the sharing model identically in both modes from the result.[c5][c16]

Known gaps

  • G1 (unimplemented; DBT copied child only): in a DBT copied child — the window between a vfork and the exec of the child's next program, where no Detcore tool runs — this call runs natively in the kernel, in fail-closed runs and under --allow-unsupported-syscalls alike: it is on the copied child's acknowledged-escape list, is not in the deterministic-refusal set (which by construction excludes ordinary forwarded calls like this one), and the copied-child gate therefore lets it through to the host (inguest-engine/src/native/copied_action.rs).[c18] On the ptrace backend (including e9patch preprocessing, which is not a backend), KVM, SaBRe and LiteInst the same call reaches the handler above. A mapping made in that window is never entered in the sharing model, so a guest whose shared futexes in that window must alias must avoid the copied-child path; there is no fallback inside the call on DBT.
  • G2 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): in a plain run on the ptrace family the returned address is the host kernel's placement at the moment the injected call runs: Detcore selects no address and rewrites none, so repeatability of the pointer a guest prints rests on the run's address-space setup outside this handler — the layout the container and loader leave — and a host or launch change that moves that layout moves every non-fixed address there; on KVM the provider places the mapping itself, as the gap below states (reverie-linuxemu/src/executor/mm.rs).[c5][linux] A guest that must name its address must fix it; there is no deterministic allocator inside Detcore's handler on any backend.
  • G3 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a shared mapping whose descriptor Detcore cannot look up is mapped successfully but entered as unresolved, and the entry is never retired: from then on every store range in that address space is treated as possibly shared, and a futex word inside that mapping still takes a private key, because the mapping itself was never entered — so two mappings of one such file can fail to alias for a shared futex where Linux gives them one word. A guest in that case has no fallback inside the call; the mapping works, only its sharing identity is missing.[c3][c7][c9]
  • G4 (by design; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a file-backed mapping is still the host file's pages outside the record/replay subscription on the ptrace family: its bytes when mapped, a write seen through a shared mapping, and a SIGBUS past the file's end are whatever the file and the host kernel do when the call and the later fault run, so a file that changes under the run, or differs between hosts, changes what the mapping reads, and Hermit makes this call repeatable only so far as that file repeats; on KVM the provider copies the bytes and gives no such fault, as the gap below states (reverie-linuxemu/src/executor/mm.rs).[c5][linux]
  • G5 (unimplemented; ptrace record and replay): under record, a shared mapping replay cannot reproduce — a shared mapping of a file that is not a regular file, of the zero device away from offset zero, of a regular file on a file system whose files map memory of their own, of the internal shmem object of a shared anonymous or /dev/zero mapping (which /proc names "/dev/zero (deleted)"), or backed by an anonymous inode; a memfd or a tmpfs file under /dev/shm is a regular file there and is recorded and backed — is not refused to the guest at this call: the mapping succeeds, the recording is marked as one replay refuses, and the guest runs on, so the failure surfaces only when the recording is replayed, where a private stand-in would have read back different bytes. A guest that must replay must keep shared mappings to regular files (and the zero device at offset zero); there is no fallback inside the call. The branches that decide this sit in the recording layer (hermit-record/src/recorder/mmap.rs); on the Detcore side the call is forwarded to that layer unchanged.[c16][c5]
  • G6 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst, where the run holds a property-area snapshot): a mapping of a live property file through a descriptor Hermit did not redirect is refused as the third refusal above instead of being mapped: a fail-closed run stops on the ptrace backend and on KVM and on LiteInst in-guest and in-guest-trap with the policy exit and ends on DBT through its runtime exit path for a call Linux would answer, on SaBRe ends only the refusing process so the run can wait on stranded, and under --allow-unsupported-syscalls every backend gives EOPNOTSUPP where Linux would return an address. A guest in that case must map the snapshot copy Hermit redirected, not the inherited descriptor; there is no live-area fallback inside the call.[c12][c13][c14]
  • G7 (unmeasured; ptrace including e9patch preprocessing, KVM, DBT, SaBRe, LiteInst): guest programs mmap_determinism, mmap_stress_determinism, anon_mapping_write and file_backed_mmap under tests/c exercise repeated, fixed, shared and reused anonymous placements, many-mapping stress with remapping, a guarded anonymous write, and a private file mapping's copy-on-write as text, and no machine-verified coverage at the pin distinguishes the forwarded address, the shared-model futex alias, the unresolved-descriptor degradation, or the replayed placement across the ptrace backend (including e9patch preprocessing), KVM, DBT, SaBRe and LiteInst; each is therefore claimed from the handler code above, not from a measured run.[c5][c7]
  • G8 (unimplemented; KVM): on KVM alone the provider places the mapping from its own allocator, copies the file bytes into guest memory and leaves past-the-end bytes zero where Linux raises SIGBUS, and refuses an anonymous call, private or shared, naming any other descriptor where Linux ignores that descriptor (reverie-linuxemu/src/executor/mm.rs), so a guest on KVM gets the provider's address, bytes and descriptor answer and has no host-kernel form of this call there.[c5]
  • G9 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): a shared call with a page-aligned negative offset through any descriptor other than the anonymous descriptor gets Detcore's EINVAL where Linux gives EBADF for a missing descriptor, EOVERFLOW for a regular file, a successful shared anonymous mapping, or a successful character-device mapping (an unaligned negative offset gets EINVAL in Linux too), so a guest in those cases meets Detcore's refusal and has no mapped fallback inside the call.[c3][linux]
  • G10 (unimplemented; ptrace including e9patch preprocessing, DBT outside a copied child, SaBRe, LiteInst): a shared anonymous call naming any descriptor other than the anonymous descriptor is filed under that descriptor's file or open description, so unrelated anonymous regions can share futex keys, or left unresolved so its words take private keys a fork does not share and every store is treated as possibly shared, either way able to misroute a shared wake where Linux keys the mapping by its anonymous flag; on KVM the provider refuses that call first (G8); a guest in that case has no correctly keyed form inside the call.[c3][c7][c9]
  • G11 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): two shared mappings of the zero device through one descriptor are entered as one object at offset zero, so their futex words collide where Linux makes a new object for each call and a wake can reach the wrong mapping; a guest in that case has no distinct-object form inside the call.[c3][c7]
  • G12 (unimplemented; ptrace record and replay): under record, capturing a successful shared mapping can end the run after the guest call already succeeded — where the file identity or access mode cannot be captured and where the zero device names no object (hermit-record/src/recorder/mmap.rs) — so a guest that mapped successfully can still lose the run to the recording; there is no record-side fallback inside the call.[c16]
  • G13 (unimplemented; ptrace including e9patch preprocessing, KVM, DBT outside a copied child, SaBRe, LiteInst): where the descriptor's record carries no file identity, a shared mapping keyed by its open description does not alias a mapping of the same file through another description, which the kernel keys by inode, so two mappings of one file can fail to share a futex word where Linux gives them one; a guest in that case has no inode-keyed form inside the call.[c3][c7]
  • G14 (unimplemented; networking trace modes): in the networking trace modes (--record-networking and --replay-networking) an mmap through a recorded channel socket never reaches this handler: the trace path ends the run with the policy-refusal exit before dispatch, where Linux maps a read-only mapping of a TCP socket for zero-copy receive and answers a writable one with a permission error, so a guest in those modes has no mmap through that socket; outside those modes this gap does not apply.[c22][linux]

Guest programs are evidence as text; no machine-verified coverage is claimed for them (G7).
