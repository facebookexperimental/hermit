stat (4)

Strategy: determinized · dispatch: typed · discussion (new)

Facts as of 403e350e9e82 · prose checked 2026-11-20 at 403e350e9e82

In short

Natively, stat copies the host filesystem's own metadata for the file a path names, so its identity numbers and its timestamps show where and when that file lives on this host. Hermit still lets the kernel look the path up and fill the result, then rewrites the guest-visible copy: the numbers come from its own pools, the access and status-change times are the configured epoch, and the modification time is a per-file virtual time it keeps. A file Detcore itself renders has no kernel metadata to copy and is answered from its rendered form instead. Known gaps: 7.

Determinism strategy

What is nondeterministic natively. stat looks a path up, following a final symbolic link, and fills its result from the inode it reaches — identity, mode, ownership, size and the access, modification and status-change times — so every value the host filesystem assigned, and every later host-side change to the file, is visible in the buffer it writes.[linux]

What Hermit does. Detcore determinizes stat when metadata virtualization is on, its default, by running the guest's own call in the kernel — its path respelled where /proc numbers are translated[c23] — and rewriting only the copy it leaves in guest memory: typed dispatch reaches the shared family handler, which finds the path target before the call can overwrite it, injects the call, reads the result back, determinizes it and writes it again.[c1][c2][c3][c4] The guest-visible inode is minted from a run-wide monotonic counter in sighting order, never from the host inode's bits, and the device likewise takes a pooled number in first-observation order, so the same schedule of sightings assigns the same pair, except where the host reuses a freed inode Detcore never retired (G6); the device half also depends on what the host connected the standard streams to, which takes its pooled number in the same first-observation order.[c8][c10] The times are neither the host's nor a clock reading taken at the call: the access and status-change times always report the configured epoch, and the modification time reports the per-file virtual value kept beside the minted inode.[c6] That virtual modification time is settled once: where no earlier write has left its bump pending, the first resolving stat settles it — a host time of exactly zero or one whole seconds, a value that timestamp-erasing tools write on purpose, is kept, and any other host time becomes the epoch — and from then on it moves only when Detcore moves it, to the bump a handled write files (global logical time; the command line refuses metadata virtualization without virtual time, so no host-clock bump reaches this call) or to the stored value of a time the guest explicitly sets.[c7][c9][c12][c13] A directory, whose host size and link count count its entries and subdirectories, instead reports 4096 bytes, eight blocks and one link.[c11]

Interface fidelity. The lookup itself is the kernel's, exactly as for the other path forms: the injected call resolves the name against the guest's working directory, follows the final link, decides whether a file is there, and fills mode, ownership, the device-file number and, outside the directory pin, size, block size and block count from the inode it reaches, because the rewrite touches none of those.[c4][c14][linux] This call takes no flags and no options to honor or coalesce, the classic result it fills has no birth-time or mount-identity field for Detcore to pass through, and a missing result pointer is answered with EFAULT.[c14][c4] Detcore's own look back at the file keeps the spellings apart: a file it renders is answered from the path as named, before any injection; a result buffer that landed on the guest's path leaves no name it can look up again; and where a procfs entry must be named for numbering, it opens an O_PATH descriptor for the guest's own path inside the guest, so a name meaning this process resolves to the guest, not to Detcore.[c4][c15][c16][c18] One invented object is hidden as the kernel's own hidden entry is: a result naming Detcore's placeholder directory becomes ENOENT, with the guest's buffer put back to what it held before the call.[c17]

Record & replay. The call is subscribed in both run and record/replay modes (code facts in the Appendix).[c2][c19] Record and replay always run without metadata virtualization, so that subscription serves the unvirtualized branch: the record-or-replay tool records the kernel's answer and replay returns it unchanged, host inode, host device and host times included: under record and replay Detcore renders no procfs file and has no placeholder directory, so neither the rendered-form answer nor the placeholder hiding on that branch ever fires.[c5][c25] The virtualized rewrite carries no recording of its own: it injects the call directly rather than handing it to the record-or-replay tool, so no replay regenerates a pooled answer for this call.[c20]

Known gaps

  • G1 (by design): the access and status-change times never move: each reports the configured epoch in every result, so a read or metadata change Linux would stamp is invisible to a guest comparing either time, and no per-file access time is kept instead.[c6]
  • G2 (by design): the virtual modification time is never re-read from the host once settled: a file changed by a writer outside the run, or in any way the handled write and time-setting bumps do not cover, keeps its settled or last bumped time even though the fresh kernel result supplies its new size, so a guest comparing modification times alone can miss the change.[c8][c9]
  • G3 (by design): a directory reports 4096 bytes, eight blocks and one link whatever it holds — a deleted directory's zero link count is preserved, and a proved procfs directory keeps its host size and count — which matches a filesystem that does not count links rather than one that does, and where a backend cannot prove that a directory is not on procfs the size half of that pin stands aside and the host size shows instead.[c11]
  • G4 (by design): the fields the rewrite leaves alone — mode, ownership, the device-file number, and a non-directory's size, block size and blocks — are the host filesystem's when the injected call runs: a filesystem that changes under the run, or differs between hosts, changes them, and Hermit makes this call's view of them repeatable only so far as the filesystem itself repeats.[c4][c14]
  • G5 (by design): with metadata virtualization turned off none of the rewrite above runs and the host inode, device and real times of the kernel's result reach the guest as they are, save that a file Detcore renders is still answered from its rendered form first and a result naming the placeholder directory is still hidden: a plain run in that configuration makes no cross-run determinism claim for this call, while in record and replay — which always run that way, with neither exception in force — replay fidelity rests on the recording returning the recorded answer.[c5][c24][c25]
  • G6 (unimplemented): host inode reuse is contained, not handled: a file that never had a name, or one that disappears without the guest removing its name, is never retired, so a named file the host gives its freed inode inherits its pooled number and its virtual modification time, and whether the host reuses the inode differs between runs.[c21]
  • G7 (unimplemented): a procfs file Detcore cannot name — threads not sequentialized, the guest mount table unreadable, a file outside the guest procfs mounts, a failed reopen, or a result buffer over the guest path — is numbered by its raw host identity instead of a rendered name, and the run records a determinism loss for it.[c22]

Tests

How a determinized result takes its epoch, its rendered or pooled inode, and its directory pins: detcore/src/syscalls/files/determinize_stat_tests.rs (determinize_stat_reads_the_mode_and_epoch_it_is_configured_with, determinize_stat_reports_one_link_for_directories_only, determinize_stat_nlink_pin_edges) — what Hermit does. That unit fixture also exercises a defensive branch the command line never builds; it is not evidence for record and replay. Which host modification times are kept as written and that the first stat settles the value for the rest of the run: detcore/src/tool_global.rs (only_exact_canonical_host_mtimes_are_kept, first_seen_mtime_is_resolved_by_the_first_stat) — what Hermit does. That pooled inodes are minted rather than passed through, that a host reusing a freed inode does not renumber the new file after the guest removed the old file's last name, and that devices are pooled by observation order: detcore/src/tool_global.rs (det_inodes_are_minted_not_passed_through, a_host_reusing_a_freed_inode_does_not_renumber_the_new_file, device_pool_remaps_deterministically) — what Hermit does. Guest programs stat_metadata_identity and file_timestamp_identity under tests/c, through the C library wrappers — which on current glibc reach the shared handler by the newfstatat entry rather than syscall 4 itself — print the determinized identity fields and the still-advancing virtual modification times end to end — what Hermit does, and interface fidelity.
