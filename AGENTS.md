# AGENTS.md

Developer guide for Hermit. Each section states the rules and names the skill
holding the detail, at `.claude/skills/<name>/SKILL.md` (also `.llms/skills/`
and `.agents/skills/`). Hermit and Reverie are developed autonomously by agents,
with asynchronous human guidance.

## Project overview

Hermit is an x86_64 Linux reproducible container. It runs a guest under the
Reverie instrumentation layer, which traps syscalls, signals, CPUID/RDTSC and
timer-preemption events. Detcore, the determinism engine and Reverie tool,
emulates each operation or forwards it to Linux and sanitizes the result,
replacing nondeterminism such as time, randomness and scheduling. It serializes
guest threads onto one logical CPU, picks the next runnable thread
deterministically, and preempts at repeatable PMU retired-branch (RCB) counts.
Hermit does not make a changing filesystem or external network deterministic;
tests needing isolation provide a stable filesystem and no external network.
See `docs/Developers/Architecture.md`, `docs/Users.md`, and `development` for
the workspace map and where to start reading.

## Build and run

x86_64 Linux only; `rust-toolchain.toml` selects Rust; libunwind development
headers are required. PMU and CPUID access vary by host: report a host
limitation rather than weakening an assertion (`development`).

```bash
cargo build --workspace                  # or: cargo check --workspace --all-targets
./target/debug/hermit run -- <program> [args...]
```

Agents run ad hoc Hermit through their harness's bounded wrapper; the official
validation and E2E runners own their bounds. Cargo manifests are generated by
`autocargo`: do not casually hand-edit them or remove `@fb-only`/`@oss-only`
markers. Scripts are rust-script `.rs` files. Before finishing a Rust change:
`./scripts/cargo-fmt-pinned.rs --workspace-members -- --check` (the pinned
nightly formatter) and `cargo clippy --workspace --all-targets -- -D warnings`.

## Test

`cargo test --workspace`, or the narrowest target while iterating
(`cargo test -p hermit-detcore`). A green Cargo run is not the full integration
matrix: more than 700 internal Buck integration tests are not fully ported.
Include the host environment when a failure depends on PMU, CPUID or CPU
features, and never mark or delete a hardware-sensitive test to green a VM.
Testing rules: `testing-principles`, `testing-with-dagrun` and
`testing-with-buck`, imported from agent-utils by
`scripts/import-agent-utils-skills.rs` and never edited here, plus the Hermit
addendum `testing-principles-hermit`.

## Backend Definition

A **backend** is a complete execution path that loads the one shared Detcore
tool through Reverie as `Detcore<XxxGuest>`. `ptrace` is the default and
best-tested; DBT and KVM are backends only where they run that full path.
e9patch preprocessing, prototypes, stubs, launch adapters and shims are not
backends. Every result names the exact backend and the exact test or guest
command with its flags, and a feature is done only when it meets its declared
level on every in-scope backend (`validation-evidence`).

## Determinism and assurance levels

Describe a run by the strongest guarantee you observed. A claim that a run
"passes" or is "deterministic" means nothing without a level.

| Level | Meaning | How it is established |
| --- | --- | --- |
| L0 | Builds and unit/integration tests pass | `cargo test` exits 0 |
| L1 | Runs deterministically under strict mode | `hermit run --strict` |
| L2 | Canonical full-observation repeat parity | `hermit run --strict --verify --verify-strict --verify-json <path> -- ...` and require JSON `bitwise_parity: true` with nonzero compared INFO-message counts |
| L3 | Memory determinism | Add `--detlog-heap --detlog-stack` to the L2 command |
| L4 | Stress-hardened | L2/L3 repeated 20x with no divergence |

`--strict` needs `--epoch` or `HERMIT_EPOCH`; tests use
`detcore_model::config::CANONICAL_TEST_EPOCH`. Default `--verify` uses the lossy
`Stripped` comparator and cannot establish L2. Report backend, log level and
relaxations with every result, for example "passes at L2 (ptrace backend,
default log level, no relaxations)". Comparators, KVM claims and reporting
rules: `validation-evidence`. Continuous virtual time is a hard requirement:
`continuous-virtual-time-is-sacred`.

## Debugging

Use Hermit's own logs and comparison tools before reading source:
`hermit --log info run`, `hermit run --strict --verify --verify-strict`,
`hermit record start --verify --verify-strict`, `hermit-verify`, and the
`log-diff`/`analyze` subcommands. Before triaging a divergence, read
[docs/DIVERGENCE_CLASSES.md](docs/DIVERGENCE_CLASSES.md). Skills:
`hermit-debugging` (nondeterminism), `determinism-regression-debugging`
(something that used to work), `deadlock-debugging` (hangs), `ci-debugging`
(validation failures).

## Change guidelines

- Reproduce a bug with the smallest test or guest first; add a regression test
  at the lowest useful layer.
- Guest-visible behavior is valid Linux behavior or a clean refusal.
- Keep fixes local to the relevant Detcore subsystem; keep unrelated changes and
  generated artifacts out of the patch.
- Preserve determinism: no host wall time, uncontrolled randomness,
  iteration-order dependence or host-specific state in guest-visible results.
- Never weaken a test, assertion, tolerance, comparator or gate to make a change
  pass.
- Don't break the demos: a change that touches a demo needs an adversarial
  reviewer to confirm the demo still runs green before it lands.
- This is a clean implementation repository: no experiments, binaries, bulk
  notes or nested git repositories. Audit every staged path before each commit
  (`repo-cleanliness`).
- New bot-authored syscall support carries `// AUTONOMOUS-BOT-IMPLEMENTED` at
  its dispatch entry and `// TODO-HUMAN-REVIEW(PR-id)` at its determinization
  block; never remove or rename either autonomously (`development`).

Full guidelines: `development`; code-quality audits: `code-elegance`.

## Review and post-facto tags

Review depth: one cold-context reviewer who is not the author by default; two
reviewers on two different models, neither the author, for engine changes (core
Reverie types, the Detcore engine and its scheduler).
Apply the `post-facto-human-review` label, and put this trailer in the commit
message, exactly for: (1) new syscall support, with both markers above; (2) a
Reverie `Tool`, `Guest`, `Backend` or syscall-interception-model change; (3) a
new determinization strategy; (4) a core Detcore scheduling change affecting how
programs are scheduled, especially race search. Routine backend-parity work is
not a trigger by itself.

```text
Post-facto-human-review: trigger-<n> (<short reason>)
```

The label routes after-the-fact human review and never waits for approval. Find
tagged changes with `git log --grep='^Post-facto-human-review:'`. Before landing
a labeled PR you must run `scripts/core-review-protocol-lint.sh` by hand
(nothing runs it for you; the gate stays unarmed): `post-facto-review`.

## Contributing and Pull Requests

- Main is gated: changes reach it only through the project's validated landing
  path. Keep main green; repair a regression before landing more work.
- Where the maintainers' `who-am-i` tool is available, its disclosure is the
  first line of a commit body and of a PR description, never in a title: the
  exact tag, verbatim; short host names are fine, fully qualified host names
  never (owner, 2026-10-09). The first section after it is **Plain Language
  Summary and Project Impact**; PR descriptions also need **Determinism**,
  **Linux Semantics** (citing the kernel source it matches) and **Validation**,
  plus **Relationship to gVisor** for KVM and **Human Review Required** for a
  labeled PR.
- Implemented means a pushed change under review (a PR, or the primary
  repository's code review) carrying the exact tested head and its validation;
  landed means on `main` by freshly fetched ancestry. Never report a weaker
  state as a stronger one.
- GitHub Actions results are supplemental evidence and gate nothing.
- A gate nobody can satisfy from what is written is a defect: fix the
  requirement everywhere it is stated.
- Read `docs/PR_SWEEP_VERDICTS.md` before sweeping open PRs: every landing
  rewrites the SHA.
- Never publish security vulnerabilities as ordinary issues.
