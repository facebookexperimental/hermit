# Developing Hermit

`AGENTS.md` states the short rules; this skill holds the detail.

## Supported environment

- x86_64 Linux. AArch64 support is incomplete; macOS is not supported.
- `rust-toolchain.toml` selects the Rust toolchain; let `rustup` and Cargo
  honor it. The workspace also builds on stable Rust 1.97.1; the pinned default
  switches to it in a separate change so validation moves in one step.
- Install libunwind development headers first: Debian/Ubuntu
  `sudo apt-get install -y libunwind-dev`; Fedora/CentOS
  `sudo dnf install -y libunwind-devel`.
- Deterministic preemption counts retired conditional branches (RCBs) on the
  CPU's Performance Monitoring Unit, so some runs need accessible hardware
  performance counters and may fail in restricted containers or VMs.
- CPUID behavior varies across hosts. The Detcore `tests_misc` RDRAND/RDSEED
  tests can fail when a VM exposes unusual CPU features or prevents CPUID
  interception. Report the host limitation; do not weaken the assertion
  without evidence of a product bug.

## Build and run

From the repository root: `cargo build --workspace` (binary
`target/debug/hermit`), or `cargo check --workspace --all-targets` for a
compile-only check. Basic invocation: `./target/debug/hermit run -- <program>
[args...]`. Agents run ad hoc Hermit through their harness's bounded wrapper;
the official validation and E2E runners own their bounds.

The Cargo manifests are generated by `autocargo` from the internal Buck
targets, as each manifest header says. Do not casually hand-edit them or remove
`@fb-only`/`@oss-only` export markers. If a task needs a manifest change, keep
it minimal and explain how the generated source stays synchronized.

## Test

`cargo test --workspace` runs the public suite. While iterating, use the
narrowest target, for example `cargo test -p hermit-detcore`,
`cargo test -p hermit-detcore-tests --test tests_time`,
`cargo test -p hermit-run`.

The `tests` and `flaky-tests` members mostly contain guest binaries that
Hermit runs in different modes; they are not the complete end-to-end matrix.
The internal Buck setup has more than 700 integration tests combining those
guests with run modes and the rr suite, not fully ported to the public Cargo
build, so a green `cargo test --workspace` does not cover every integration
test. When a test depends on PMU access, CPUID interception or particular CPU
features, include the environment in failure reports. Never mark or delete a
hardware-sensitive test merely to make a local VM green.

## Lint and format

The checked-in rustfmt configuration needs the nightly formatter pinned in
`ci/rustfmt-toolchain.toml`; stable rustfmt ignores its nightly-only options.
`scripts/cargo-fmt-pinned.rs` runs `cargo fmt` with that formatter and refuses
any other. Before finishing a Rust change:

```bash
./scripts/cargo-fmt-pinned.rs --workspace-members -- --check
cargo clippy --workspace --all-targets -- -D warnings
```

`make fmt` applies formatting. Fix warnings in code you change; add a broad
`allow` only when the warning is intentionally inapplicable and the reason is
documented.

## Scripts

- Project scripts are rust-script `.rs` files with the shebang
  `#!/usr/bin/env -S rust-script --force`. `--force` delegates included-module
  and local-path dependency freshness to Cargo instead of rust-script's
  main-file-only executable cache; `env -S` needs GNU coreutils 8.30 or newer.
- Prefer rust-script over Python for all new scripts; install it with
  `cargo install rust-script` if missing.
- `scripts/` is for repository-wide utilities; co-locate actions over a
  directory's data with that directory (`docs/DIRECTORY_ACTIONS.md`). Shared
  support may live under `scripts/lib/`.
- Standalone CLI scripts call `scripts/lib/rust_script_prelude.rs::init`
  before producing output so Unix pipelines terminate cleanly on `SIGPIPE`.

## Workspace map

The 22 members of the root `Cargo.toml` workspace (it is authoritative; the
`reverie` submodule is a path dependency, not a member):

| Path | Role |
| --- | --- |
| `hermit-cli` | Main `hermit` CLI and the `hermit` library: run, record, replay, log-diff, analyze, container orchestration. |
| `hermit-cdylib` | `libhermit.so`, the shared-object form of the `hermit` library, kept out of `hermit-cli` so Cargo can pipeline it. |
| `hermit-run-ptrace` | The plain ptrace run: the root of Detcore's ptrace instantiation, its own crate so it builds in parallel. |
| `hermit-run-kvm` | The KVM run: the root of Detcore's KVM instantiation, its own crate so it builds in parallel. |
| `hermit-record` | The ptrace recording tool, compiled apart from the `hermit` library so its Detcore instantiation builds in parallel. |
| `hermit-replay` | The ptrace replay tool, compiled apart in the same way. |
| `hermit-record-format` | The record/replay event format shared by recording and replay. |
| `detcore` | Determinism engine and Reverie tool: scheduler, virtual time, syscall handling, content digests, CPUID handling, record/replay behavior. |
| `detcore-model` | Shared deterministic state and model types: PIDs, file descriptors, futexes, schedules, logical time. |
| `detcore-liteinst` | In-guest Detcore runtime preloaded into the guest for `--backend=liteinst`. |
| `inguest-engine` | The shared compiled in-guest Detcore engine for ordinary native entry shims. |
| `detcore/tests` | Detcore's integration tests (package `hermit-detcore-tests`), separate so the library's unit-test binary does not wait for them. |
| `detcore/tests/testutils` | Helpers for Detcore integration tests. |
| `detcore/tests/lit-guests` | Private package building the Rust programs `detcore/tests/lit`'s fixtures run as `%me`, for `hermit-cli/tests/lit.rs`. |
| `hermit-verify` | Verification executable for stress, trace, schedule and replay checks. |
| `hermit-resources` | Resource accounting and limit types shared by Hermit and Detcore. |
| `hermit-install` | Private build helper that stages feature-gated third-party backend resources for tests and development. |
| `ci/manifest-plan` | Private generator and validator for the E2E manifest, test inventory and test-selection artifacts. |
| `common/test-allocator` | Test allocator and supporting test binary. |
| `common/test-workdir` | Per-run filesystem isolation for Hermit tests inside the pinned root. |
| `tests` | Guest programs for integration scenarios: time, futex, network, pipe, scheduling, RDTSC. |
| `flaky-tests` | Intentionally racy guests that demonstrate deterministic scheduling and chaos mode. |

## Architecture and where to start reading

Reverie is the external process-instrumentation layer: it traps guest
syscalls, signals, CPUID/RDTSC operations and timer-preemption events, and can
inject syscalls into Linux. `hermit-cli` creates the container and runs Reverie
with Detcore as its tool. Detcore emulates an operation or forwards it to Linux
and sanitizes the result. Its implementation splits between `tool_local`
(events near each guest task) and `tool_global` (shared deterministic state),
which communicate through RPC. Start investigations in:

- `detcore/src/syscalls/` for syscall-specific behavior;
- `detcore/src/scheduler.rs` and `detcore/src/scheduler/` for scheduling;
- `detcore/src/tool_local.rs` and `detcore/src/tool_global.rs` for event flow
  and shared state;
- `detcore/src/cpuid.rs`, `detcore/src/time.rs` and
  `detcore/src/record_or_replay.rs` for those subsystems;
- `hermit-cli/src/bin/hermit/` for CLI subcommands;
- `hermit-record/src/recorder/` and `hermit-replay/src/replayer/` for
  recording and replay, `hermit-record-format/` for their shared event format;
- `docs/Developers/Architecture.md` (overview) and `docs/Users.md`
  (user-facing behavior).

## Change guidelines

- Reproduce a bug first with the smallest applicable test or guest program.
- Keep syscall fixes local to the relevant Detcore subsystem when possible.
- Preserve determinism: no host wall time, uncontrolled randomness,
  iteration-order dependence or host-specific state in guest-visible results.
- Add a regression test at the lowest useful layer: guest programs in `tests`
  or `flaky-tests`; Detcore unit and integration behavior under `detcore`.
- Run the focused test while iterating, then the workspace test, format and
  Clippy checks. Document checks the current hardware cannot execute.
- Keep unrelated changes and generated artifacts out of the patch, and audit
  every staged path before committing (`repo-cleanliness` skill).
- Don't break the demos: if a change touches a demo, an adversarial reviewer
  must confirm the demo still runs green (not only code-review it) before it
  lands.

## Bot audit markers for new syscall support

New syscall support authored by a bot leaves two narrowly scoped
determinization breadcrumbs:

- `// AUTONOMOUS-BOT-IMPLEMENTED` at the new dispatch or classification entry;
- `// TODO-HUMAN-REVIEW(PR-id)` at the implementation or determinization
  block, with `PR-id` replaced by the introducing pull request.

Both are required for new syscall support. They are not blanket markers for API
changes, backend work or routine parity fixes. Never remove or rename either
marker autonomously. New syscall support is also post-facto trigger 1
(`post-facto-review` skill).
